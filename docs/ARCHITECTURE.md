# Architecture

Living document. Update it in the same change that alters the shape described here.

## Three parts

```
 shell (Tauri 2, Rust)  ──spawn──▶  daemon (Node 24, TypeScript)  ──serves──▶  ui/ (static HTML/CSS/JS + 98.css)
        │                                   │
        │  stdin pipe (held open)           │  http://127.0.0.1:<random port>
        │  stdout: "KANBAN95 port=<n>"      │  GET /          → ui/index.html
        └──── WebviewWindow(External url) ──┘  GET /health    → {"ok":true}
                                            │  /api/*        → REST over <repo>/.kanban95/board.db (operator UI)
                                            │  POST /mcp     → MCP tools for agents, bearer grant required
                                            │  WS /pty/<key> → an agent's terminal, both ways (xterm.js)
                                            │  WS /events    → board events for the UI (sounds, ticket changes)
                                            │  GET /voice-model/* → the speech model's files (manifest-listed only)
```

- **Shell** (`shell/`): owns the OS windows and the lifetime of every daemon it hosts, one per open project, shown one at a time in the main window or each in its own window (see Hosted boards). No app logic. Installed, it runs the Node it ships with (a sidecar next to its exe) on the daemon staged with it; in dev, `node` from PATH on `daemon/dist/server.js` in the repo; see Packaging. Its error dialog (`error_dialog` in `shell/src/main.rs`: a failed handshake, a second crash, a failed install) is a native modal box on Windows (`MessageBoxW`) and macOS (`rfd::MessageDialog`), shown before any window exists or after the webview is gone; the text also goes to stderr, so a Terminal run shows it. On macOS rfd runs the box on the main thread itself, waiting on it from a background thread while the event loop runs; a call from a background thread after the loop has stopped cannot show it and leaves only the stderr line.
- **Daemon** (`daemon/src/`): the only process with state. The repo it serves is `argv[2]`; without one, the Start here project, else the last shown board, else the first project in `projects.json` whose folder exists, else first-run setup. `start()` refuses a repo folder that does not exist (`openDb` would recreate it); the error is printed as the first stdout line, so the shell's "did not start" dialog shows it (Daemon lifetime → Startup without an argument). Its modules:
  - `attachments.ts` stores, lists and removes the files attached to a ticket under `<repo>/.kanban95/attachments/<id>/`.
  - `boards.ts` is the other boards on this machine: the running registry (`~/.kanban95/running/`), and opening or focusing another project's board for Start → Projects (see Daemon lifetime).
  - `context.ts` builds the variables for a ticket and records the rendered prompt on a `runs` row (`startRun`) before anything is spawned (see Prompts below).
  - `db.ts` opens and migrates the per-repo SQLite file (schema in `docs/DATA.md`).
  - `deliverables.ts` records, after a merge lands, one Inbox entry per deliverable folder it touched and opens one in the OS file manager (`docs/OPERATOR.md` → Deliverables).
  - `git.ts` creates and removes the per-ticket worktree and merges the base into it (`syncWorktree`, on submit and in the merge queue).
  - `grants.ts` mints, verifies, revokes bearer grants and writes audit rows (`docs/SECURITY.md`).
  - `janitor.ts` removes worktrees, branches, session dirs, grants and old scrollback nobody needs any more.
  - `launcher.ts` launches an agent (worktree, run row, grant, session dir, argv, pty) and tears it down (see Launch below).
  - `lifecycle.ts` is the ticket state machine: one table of transitions, `apply(board, ticket, event)`, the runner's `tick` and the silence watch that flags an agent whose transcript stopped growing (`docs/LIFECYCLE.md`).
  - `limits.ts` asks each CLI for its account's usage limits and caches them 5 minutes (`docs/OPERATOR.md` → Limits).
  - `mcp.ts` is the agent-facing MCP server at `/mcp`: one table of tools, each with a description, a role access cell and a handler, enforced per grant and audited per call.
  - `mcp-doc.ts` renders `docs/MCP.md` from the `mcp.ts` tool table.
  - `memlog.ts` appends free memory and each live session's process-tree working set to `.kanban95/memory.log` every 30 s, plus a line per launch, kill and merge (`docs/DATA.md`).
  - `merge.ts` is the one serialized merge queue.
  - `pick.ts` is the native file or folder dialog the shell opens for the page: one open request per daemon, its token, its result and its 5-minute timeout (Hosted boards, `pick=`).
  - `pty.ts` spawns the CLI in a pseudo-terminal with an env allowlist and keeps a scrollback capped at 2000 lines and 2 MiB.
  - `ready.ts` is the readiness check behind `GET /api/ready`, the status bar's "Not ready:" line and the brainstorm and operator briefs' `{{ready}}` (`docs/OPERATOR.md` → Readiness).
  - `requirements.ts` asks git, Claude Code and Codex for `--version` for the Requirements list on the setup page and in Settings → Agents (`docs/OPERATOR.md` → First run).
  - `server.ts` is the HTTP plumbing (bind, origin guard, static files, `/health`, routes `/api/*` to `api.ts`).
  - `setup.ts` is first-run setup and the missing-data-folder page: `GET`/`POST /api/setup` (the GET answers `{data, shell}`, the default data folder and whether the shell hosts the page, which shows its Browse buttons only then), `POST /api/setup/retry`, `GET /api/requirements` and the setup page's way to a dialog (`POST /api/pick`, `GET`/`POST /api/pick/<token>`) on a daemon that serves no board, `setupPage` (setup.html as served), and `firstProject` for a start without an argument.
  - `settings.ts` resolves the data folder through the pointer (`boardHome`, Data folder pointer below), reads and writes the operator's `~/.kanban95/models.json`, `settings.json` (schema-checked), `projects.json` (adds the served repo on start) and `preferences.md`, resolves a repo's own copy of models.json, settings.json and preferences.md (`<board home>/projects/<repo key>/`, used whole when it exists, else the global file; `repoKey` is shared with the worktrees root), lists the models the installed CLIs know (`knownModels`, for the Settings dropdowns), and resolves a run's CLI, model, effort and executable. Every write of these files, and `addProject`'s read and write of projects.json, runs under one lock shared by every daemon on the board home (an IMMEDIATE transaction on `settings.lock`, waiting up to 10 s; the OS releases it when a daemon dies), and is written to a temp file named for the writer (`<file>.<pid>-<uuid>.tmp`) then renamed over the file; a failed write removes only its own temp file.
  - `templates.ts` copies the default prompt templates from `templates/` into `<repo>/.kanban95/templates/`, keeps unedited copies in step with the defaults on start (see Prompts below) and renders them.
  - `trust.ts` pre-trusts the repo root for Claude Code before a launch.
  - `update.ts` passes updates between the shell and the UI: asks the shell to check, relays its reports, refuses Update now while agents run (see Updates below).
  - `voice.ts` downloads, verifies and serves the speech model (see Voice below).
- **UI** (`ui/`): plain files served by the daemon, ES modules, no bundler (see UI below). 98.css, xterm.js and transformers.js are vendored in `ui/vendor/` so nothing loads from a CDN at runtime.

## Port handshake

1. Shell mints a random secret and spawns the daemon on the canonical repo path with it in `KANBAN95_SECRET` (environment, never argv), plus `KANBAN95_SHELL=1` and `KANBAN95_SHELL_ID=<shell pid>`, and `stdin` and `stdout` piped.
2. Daemon binds `127.0.0.1:0` (kernel-assigned port; `KANBAN95_PORT` fixes it, for debugging), then prints exactly one line to stdout: `KANBAN95 port=<n>`.
3. Shell reads that line, builds `http://127.0.0.1:<n>/?k95=<secret>` and creates the main webview window on it (the first daemon's handshake runs after Tauri starts, Daemon lifetime → Splash); the daemon trades that for an HttpOnly cookie `k95-<n>` and redirects to `/`. Any other first line, or none within 60 s (`HANDSHAKE_WAIT`; 20 s, `OPEN_WAIT`, for a daemon started by `open=`: the shell is already up, so a slow start there is a stuck one), is a handshake error; the shell kills the child, shows an error dialog and exits (for a daemon started by `open=`, only that board fails, and the board that asked is told, Hosted boards).
5. Shell keeps reading daemon stdout line by line to its own stderr prefixed `[daemon]`, so the pipe can never fill and block the daemon, and acts on the lines that are commands (Hosted boards).

## Daemon lifetime

- **No console window**: in a release build the shell is a GUI program (`windows_subsystem = "windows"`), so `node()` starts the daemon with `CREATE_NO_WINDOW` (0x08000000) or Windows would open a visible console for node.exe; it is the only `Command` the shell runs on Windows (the opener and the macOS login-shell probe are not Windows code). The dev build (`cargo run`, `npm run dev`) is a console program by design and leaves the flag off, so the daemon shares its console and logs stay visible.
- **Job object**: the shell's first act is to put itself in a Windows job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The daemon and WebView2's `msedgewebview2.exe` processes inherit it, and only the shell holds the job handle, so when the shell process ends for any reason (window close, crash, `taskkill /f`, logoff, shutdown) Windows kills every process in the tree.
- **WebView2 profile per shell**: every window of a shell uses `%LOCALAPPDATA%\dev.kanban95.shell\boards\<FNV-1a of the canonical path of the repo the shell started with>`; the boards it hosts and its popped-out windows share it. A profile has one `msedgewebview2.exe` browser process, started by the first shell to open it and therefore in that shell's job; with one profile shared across shells, closing the first shell killed every other shell's webview. The UI keeps no browser storage, so a profile holds nothing of value. When `WEBVIEW2_USER_DATA_FOLDER` is set, the shell passes that folder instead (WebView2 would prefer the variable anyway; passing it keeps Tauri from creating an unused folder).
- **Restart once**: one supervisor thread polls every hosted daemon every 250 ms, and the rules below hold for each daemon on its own. Exit code 75 means the daemon asked to be restarted (Start → Restart board): it is restarted as below every time, without spending the one unexpected restart. Any other exit is unexpected. The first unexpected exit starts a new daemon with a fresh secret, moves the navigation lock to its new port and navigates the window that shows it, if any, to `/?k95=<secret>` there (a new origin; the UI keeps no browser storage, so window places and the startup layout come back from `.kanban95/ui.json`). The restart runs on its own thread, outside the hosted-board table lock, so a new daemon that stalls before its handshake blocks no other board, switch, close or exit; closing that board or shutting down the shell kills the waiting child, and a handshake that lands after its board was closed is dropped (each restart has a generation the board must still be waiting on). A second exit of the same daemon, or a failed restart, shows a native error dialog and drops that daemon only; the shell exits when it was the last. No loop. `cargo test --manifest-path shell/Cargo.toml` covers this with stand-in daemons that exit at once.
- **Restart board**: `POST /api/restart`. When the daemon runs from a repo checkout (its install root has `daemon/src`), it first runs `npm run build` there (120 s timeout); a failed build answers `409` with the compiler output and the board keeps running the code it has. Then it answers `202 {restarting: true, shell}`, shuts down as `close()` does (agents killed through the normal path; while closing, their exits do not flag their tickets, so `recover` resumes them on the next start), and exits with code 75. An installed `app/` has no `daemon/src`, so nothing is built (`installed()` in `lifecycle.ts`). The shell spawns the daemon with `KANBAN95_SHELL=1`; started by hand without it, the reply says `shell: false` and the process simply exits. Shell changes are not picked up: they need `cargo build` and a full relaunch.
- **First start on a plain folder**: before recording `startCommit`, `start()` runs `initRepo` (`git.ts`). No `<repo>/.git`: `git init`, unless the folder has `.gitattributes` or `.github` (`GIT_COPY_MARKS`): that is a repo copied without its `.git`, and a fresh init would cut it from its history and remote, so it fails with `gitError` saying to clone instead. No commit yet (also a repo that exists but is empty): a `.gitignore` unless one exists (`node_modules/`, `dist/`, `build/`, `.env`, `.env.*` except `.env.example`/`.env.sample`/`.env.template`, and `.kanban95/` plus each line of `.kanban95/.gitignore`), then `git add -A`, `git rm --cached` of every env file by that same name rule (`isSecretPath`, so an existing `.gitignore` that does not cover them changes nothing; contents are never read), then `git rm --cached` of every file over 10 MB (`FIRST_COMMIT_MAX_BYTES`), each appended to `.gitignore` as an anchored `/<path>` line (an existing `.gitignore` too) so it stays out of the commit and every worktree, with one stderr line naming them and saying to remove the line and `git add` the file to commit it (leaving them out was chosen over stopping the start: the board still starts and the operator loses nothing), and one commit "Start the Kanban95 board" with `-c user.useConfigOnly=true`, so it is the operator's configured identity or nothing (no trailer). A repo with commits is untouched; a second start adds nothing. Each step is logged to stderr. An env file already in the index before the board ran (the operator staged it) is not unstaged for them: no commit is made and the error says `git rm --cached -- <path>` or commit by hand. On failure (git missing, no `user.name`/`user.email`, a staged env file) the daemon still starts: `board.gitError` holds the message, `GET /api/runner` returns it as `gitError`, the Board's status bar shows it, and every ticket launch fails with it (`launch failed: …`). It is read once, so fixing git needs a board restart. With no remote, nothing is pushed (`docs/LIFECYCLE.md` → Push).
- **Start timing**: `start()` in `server.ts` writes one stderr line per step before the port line, `[start] <step> <ms>`, the ms since the step before: `data home`, `db`, `brain`, `templates`, `projects`, `git init`, `file mode`, `template commit`, `rev-parse`, `listen`, `register`, `janitor`, `release`, `recover`, `tick`. Daemon stderr is not in the shell log; start the built daemon by hand (`KANBAN95_SECRET=<64 chars> node daemon/dist/server.js <repo>`) to read them.
- **Git at start is capped**: every `git()` call (`git.ts`) a start step makes runs inside `gitWithin` with one shared budget, `START_GIT_MS` (5 s) per call. A call that takes longer is killed, and every later `git()` call of that start fails at once without running, so a stuck git (a hook, a credential or signing prompt, a `.git/index.lock` left behind) holds the port line for one 5 s wait at most. `initRepo` then sets `board.gitError` ("git did not answer within 5 s ...") and the board starts with launches refused, as for any git failure; the template commit, `rev-parse`, `core.fileMode` and the janitor's prune are logged and skipped. Git calls after the port line are not capped.
- **File modes on a carried drive**: after `initRepo`, `start()` runs `guardFileMode` (`git.ts`): on macOS, a repo on a volume that is not APFS or HFS gets `core.fileMode false` if unset (Working on the board → A repo on a carried drive). A failure is logged and does not stop the start.
- **Stale daemon**: at start the daemon records `git rev-parse HEAD` of the repo (`board.startCommit`; unset in a repo with no commits, and then nothing below runs). After each successful merge the queue runs `git diff --name-only <startCommit> HEAD -- daemon/ templates/ shell/ package.json package-lock.json` (templates/ because the daemon copies the shipped templates into the repo on start); a non-empty list sets `board.stale` to `'shell'` when every path is under `shell/`, else `'daemon'`, and emits `changed(null)`. `GET /api/runner` returns it as `stale: false | 'daemon' | 'shell'`; the UI shows the status-bar line and the tray's Restart badge from it (`docs/OPERATOR.md` → Restart board). While it is `daemon` the runner launches no backlog ticket (`shell` holds nothing: agents never run on the shell), and a `daemon` board under the shell restarts itself through Restart board once no ticket is left to finish (`docs/LIFECYCLE.md` → Restart after a merge). A restart records a new commit, so it clears. An installed board (`installed()`: its install root has no `daemon/src`) never goes stale: it runs `app/`, not the repo's code, so a merge only updates the release-pending count below.
- **Release pending**: only in the Kanban95 repo itself (`isKanban95`: it has `shell/tauri.conf.json` and a `package.json` named `kanban95`). At start and after each merge, `releasePending` runs `git describe --tags --abbrev=0 --match v*` and counts `git rev-list <tag>..HEAD -- daemon/ shell/ templates/`; a non-zero count sets `board.release = {since, commits}`. No `v*` tag: nothing is pending. `GET /api/runner` returns it as `release: {pending: true, since, commits}` (`docs/LIFECYCLE.md` → Release board).
- **Data folder pointer**: `~/.kanban95/home`, one line, names the data folder (settings, models.json, preferences, projects.json, the global brain, the running registry, voice models), so it can live on an SSD carried between machines. `boardHome()` in `settings.ts` reads it on every call and is the only way to that folder; absent, the data folder is `localHome()`, `~/.kanban95` (or `KANBAN95_HOME`). Worktrees stay under `localHome()` whatever the pointer says (`docs/DATA.md`). Only setup writes it (`setBoardHome`), before anything is created in the new folder; changing it later is not supported (`docs/OPERATOR.md` → First run). When the pointer names a folder that is not there, `missingHome()` says so: the daemon starts `startSetup` instead of a board, with or without a repo argument, and `/` serves setup.html rewritten by `setupPage` (not-found text, path filled in, no project box, **Retry** shown). `POST /api/setup/retry` answers 400 while the folder is still missing, else exits 75; `POST /api/setup {data}` writes the new pointer and exits 75; the restart then finds the folder. Writers reach the folder through `dataHome()`, which refuses a missing pointer folder and creates only the local home, so nothing recreates a carried folder empty.
- **Startup without an argument**: a shell started from the Start menu or the Dock has no repo argument and no useful cwd. The shell then starts the daemon with no argument and keys that board `""` (window title `Kanban95`). The daemon picks the board with `startupProject` (`setup.ts`), in order: the `startup` path in the global `settings.json` when it is not `"last"` and its folder exists; else the path in `<data folder>/last-board` when it is listed in `projects.json` and its folder exists; else the first listed project whose folder exists. The page writes `last-board` on load through `POST /api/last-board` (`window: "own"` from a popped-out window writes nothing), and a missing or unparsable file is ignored. When the list is empty, the daemon runs first-run setup instead of a board: `startSetup` in `server.ts` binds the same way and prints the same handshake but opens no db, brain, registry entry or repo, and serves `ui/setup.html` at `/` and `GET`/`POST /api/setup` (`setup.ts`) and `GET /api/requirements` behind the same secret cookie; `/mcp` and every other `/api` route answer `404`. A setup daemon over no repo was chosen over a temporary empty repo: nothing to create or clean up. `POST /api/setup {data, project}` refuses an empty or relative data folder and a project folder that is not an existing directory (`400 {error}`, shown on the page), then writes the pointer, adds the project to `projects.json` in the new data folder and, once the reply is sent, exits 75; the shell restarts it as for Restart board, with no argument, and this time it finds the project. ponytail: a board keyed `""` that another board then opens by path gets a second daemon; re-keying the shell's table on the served repo would fix it.
- **Splash**: every shell launch spawns its first daemon, then starts Tauri and finishes the handshake on a thread (`Host::boot`). If the daemon has not answered within 400 ms of its spawn, a small always-on-top splash (`shell/splash.html` and the 32 px icon, served from the `k95splash` URI scheme; a `data:` URL would need tauri's `webview-data-url` feature and a new crate) shows "Starting Kanban95..."; it is destroyed once the main window opens, or hidden before the error dialog of a failed handshake. A faster daemon goes straight to the board. Restart, switch, popout and `open=` never show it. `KANBAN95_SPLASH_TEST=1` holds the first handshake 3 s to see it. The scheme answers each file with its `Content-Type` (`splash_response`). The URL is `http://k95splash.localhost/` on Windows and `k95splash://localhost/` on macOS. The navigation lock (`on_splash`) compares scheme, host and port, not `Url::origin()`: a custom scheme has an opaque origin that never equals another, even its own, and WKWebView asks the lock about the first load too. Comparing origins made macOS cancel that load and show a blank white window.
- **Kill on exit**: on Tauri's `RunEvent::Exit` the shell marks its table done (which stops the supervisor and kills a daemon still starting once it reports its port) and calls `kill()` then `wait()` on every hosted and closing daemon.
- **Shell log**: a release shell is a GUI program whose stderr goes nowhere, so `log()` in `shell/src/main.rs` appends board-breaking failures, one ISO-timestamped line each (multi-line texts joined with spaces), to `%LOCALAPPDATA%\Kanban95\shell.log` on Windows or `~/Library/Logs/Kanban95/shell.log` on macOS, creating the folder. The path is built from `LOCALAPPDATA`/`HOME`, not Tauri, because the first failure can come before Tauri starts. `KANBAN95_SHELL_LOG=<file>` points it elsewhere. At start a log past 1 MB is emptied (`LOG_CAP`, a ponytail ceiling). Every error dialog ends with "Details: <path>". What is logged:
  - every text an error dialog shows (Could not start Node.js, a failed handshake with the daemon's first line, a daemon that stopped again after one restart, a failed restart, a main window that would not open, an update that did not install)
  - a closed daemon killed after `STOP_WAIT`
  - an update check that failed
  - an update download or install that failed
  - a popped-out window or the splash that could not open

  Nothing else: no `[daemon]` echo, no successful start, no update check that found nothing, nothing about agents or tickets. Daemon stderr is not captured by the shell, so it is not logged. Log texts carry no secret and no `?k95=` URL; check that before adding a call.
- **Running registry**: once it has its port, the daemon writes `~/.kanban95/running/<pid>.json` (`{pid, repo, port, started, shell, agents, key}`, `docs/DATA.md`; `key` is 32 random bytes another board sends to file a ticket here, SECURITY.md → Registry key; `shell` is `KANBAN95_SHELL_ID`, null when started by hand; `agents` is the daemon's live session count, rewritten on every `change` event that finds it different, so it moves when a session starts or ends), and `close()` removes it, as does the process's `exit` handler. Closing the window kills the daemon outright (Kill on exit, the job object), so neither runs and the entry stays behind: every reader (`running()` in `boards.ts`) deletes an entry whose pid is dead, and `GET /api/projects` marks a project running only for a live one.
- **Another project's board** (Start → Projects): `POST /api/projects/open` starts a board on a listed project that is not running. A child of the daemon would live in this board's kill-on-close job, which allows no breakaway (libuv's `detached` does not ask for it), and die with it; so on Windows the new process is created through WMI (`Win32_Process.Create` from one PowerShell call), outside the job, with this daemon's environment and hidden (the dev shell is a console program: its console stays hidden, its window shows). From a checkout it runs `shell/target/debug/kanban95-shell.exe <path>` (`kanban95-shell` on macOS) as `npm run dev` last built it, not `cargo run`: that relinks the exe every time (Working on the board → Windows) and on Windows fails while this board holds it open. With no build there it answers `no shell build at <path>: run npm run dev once`. Installed, it runs the `.exe` next to `app/`; the installed Mac app finds none and answers with an error (`open -n -a <bundle> --args <path>` would be the upgrade). `POST /api/projects/focus` brings a running board's window to the front: one PowerShell call finds the top-level window titled `<folder name> — Kanban95` and calls `SwitchToThisWindow`, which restores a minimized window and is not held back by the foreground lock (`AppActivate` and `SetForegroundWindow` only flash the taskbar button from a process that did not get the last input). Two projects with the same folder name share a title; the first window found wins. macOS: nothing is focused and the status bar says so. Focus is for a board in another shell. Within this board's own shell, the daemon asks the shell instead: `open` with `where: 'here'` and `switch`, `popout`, `dock`, `close` write one `KANBAN95 <cmd>=<canonical path>` line to stdout (`tellShell()` in `boards.ts`, Hosted boards). A project is hosted by this shell when its running entry has the same `shell` as this daemon's. `close` of this board's own path is allowed: the shell closes its stdin and the normal shutdown runs (Stdin EOF).
- **Sleep**: only under the shell (`KANBAN95_SHELL=1`). A board with no live session (`sessions` in `launcher.ts`) and no `/events` websocket client is idle. One timer (`doze` in `server.ts`) is armed when the board turns idle, on start, on a `change` event that finds no session, or when the last `/events` client leaves, and cleared when a session starts or a client connects; no polling. After `sleepAfterMinutes` (`settings.json`, per project over global, default 30, 0 never, read when the timer is armed) it writes `KANBAN95 close=<own repo>` once (`tellShell`), and the shell closes its stdin (Stdin EOF). The page in the main window or in a popped-out window holds an `/events` client, and a brainstorm or operator terminal is a session, so a board on screen or running anything never sleeps. A board started by hand never sleeps.
- **Stdin EOF**: the daemon holds `process.stdin` open and, when it ends, shuts down as Restart board does (every session's process tree killed first, 15 s cap) and exits with code 0. The job object would end the agents on Windows anyway; on macOS nothing else would. The shell never writes to it; the pipe simply closes when the shell process dies, including on a crash. An orphaned daemon is therefore not possible. Consequence: if you start the daemon by hand with stdin closed (`< /dev/null`, `stdio: 'ignore'`), it exits immediately after printing the port. That is intended.

### Hosted boards

One shell hosts several daemons and moves its windows between them, like virtual desktops. `Host` in `shell/src/main.rs` keeps a table keyed by canonical repo path (Windows' `\\?\` prefix dropped, so it matches the daemon's spelling). Each row holds:
- the child, its stdin held open
- its port and secret
- where it shows: `docked` (in the main window when switched to) or `own` (its own window, label `board-<FNV-1a of the path>`)
- whether its one unexpected restart is spent

At start the table has one daemon, the shell's repo argument (else keyed `""`, Daemon lifetime → Startup without an argument), docked and shown in the main window: started by hand, the shell looks as it always did. A window loads one page at a time. Showing a board navigates the window to that daemon's `/?k95=<secret>` and sets the window title from its repo (`title()`); the UI keeps no browser storage, so the reload loses nothing. The window keeps its full screen state across a switch: the navigation unloads the page's fullscreen element, and the shell ignores the `ContainsFullScreenElementChanged` false that comes between `NavigationStarting` and `NavigationCompleted`. Tauri (tauri-runtime-wry 2.12) registers its own handler for that event, which sets the window to the page's state with no exception, so `follow_page_fullscreen` removes it (its token is the one just before the shell's) and the shell's handler is the only one. When the new page has loaded in a full screen window, the shell puts it back in fullscreen with the DevTools method `Runtime.evaluate` and `userGesture: true` (a page cannot call `requestFullscreen` on load), so Start → Full screen reads "Exit full screen" and one F11 leaves. The steps above are WebView2 (Windows). On macOS WKWebView ends the page's fullscreen when the page unloads and has no event to hold it, so `navigate_keeping_fullscreen` reads `WKWebView.fullscreenState` before the navigation; if it was full screen, it polls every 100 ms (up to 10 s) until the new page has loaded and the exit animation is over (`fullscreenState` back to not in fullscreen), then runs `requestFullscreen()` with `evaluateJavaScript`, which WKWebView treats as a user gesture. Asking while the exit animation still runs is lost: the page enters and drops out again. A windowed switch keeps its size. The navigation lock allows every hosted daemon's origin and nothing else (`docs/SECURITY.md` → Webview).

After its port line, every line a daemon prints is a command when it matches one of these (`<path>` is the canonical repo path, UTF-8, the rest of the line):
- `KANBAN95 open=<path>`: start a daemon on that repo (fresh secret, the shell's environment plus `KANBAN95_SHELL=1` and `KANBAN95_SHELL_ID=<shell pid>`), docked, and show it in the main window once its port line arrives (within `OPEN_WAIT`, 20 s). Already hosted: show it, or focus its own window. A failed start (a handshake error or no port line in time) shows the error dialog and is posted to the daemon that printed the line, by its port and secret, as `POST /api/open/shell` with `{path, error}` (`Effect::Tell`, no `Origin`, as for update reports); that daemon sends an `open-failed` event and its status bar says "<folder> did not open: <reason>".
- `KANBAN95 switch=<path>`: show that docked daemon in the main window.
- `KANBAN95 popout=<path>`: open a second window on it with the main window's options (title, profile, fullscreen follow, navigation lock) and mark it `own`. The window opens on the daemon URL with `#own`, which survives the `?k95=` redirect, so the page knows it is popped out and offers Dock in Start → Projects. If the main window showed it, the main window moves to another docked daemon; when there is none, nothing happens and a `[shell]` stderr line says so.
- `KANBAN95 dock=<path>`: close its own window, mark it docked and show it in the main window.
- `KANBAN95 close=<path>`: close its stdin, so it shuts down as on Stdin EOF, drop it from the table and, if the main window showed it, show another board there (a docked one, else an own one docked back). The supervisor kills it if it still runs after 15 s. Closing the last one exits the shell once it has stopped.
- `KANBAN95 restart=<path>`: close its stdin, so it shuts down as on Stdin EOF, and start it again as on exit code 75 (Daemon lifetime → Restart once) in the same place, without spending its one unexpected restart. The supervisor kills it if it still runs after 15 s. Settings → Board → Data folder sends it for every other board this shell hosts.
- `KANBAN95 check=<path>`: check for a newer release (Packaging → Updates). The shell answers the daemon that printed the line, by its own port and secret, so the path is not looked up.
- `KANBAN95 checknow=<path>`: the same, from Settings → Board → Check for updates: never skipped, and "up to date" or a failure is reported too.
- `KANBAN95 update=<path>`: download and install the release found by the last check (Update now).
- `KANBAN95 pick=<path> <kind> <token>`: open a native dialog, a folder picker for kind `folder` and a file picker for `file`, over the window that shows that daemon, and post the result to the daemon that printed the line, by its port and secret, as `POST /api/pick/<token>` with `{path}` or `{cancelled: true}` (no `Origin`, as for update reports). `<path>` is empty for the setup page, and the kind and token are read from the end of the line. The dialog is built on the main thread (`rfd`'s async dialog, which macOS needs there) and awaited on its own thread, so no window waits on it. The token is lowercase hex the daemon minted; anything else is ignored.

Any other line, or a command for a board not in that state, changes nothing (a `[shell]` line says why).

- A hosted board that is not on screen and runs no session writes `close=` for itself after `sleepAfterMinutes` (Daemon lifetime → Sleep). It then shows as not running; Open here starts it again.
- Closing a popped-out window stops its daemon as `close=` does. Closing the main window exits the shell and stops every hosted daemon (Kill on exit).
- Threads: one reader per daemon, which ends at that daemon's stdout EOF; one short-lived thread per `open=` while the daemon starts; one per update check, install or report (Packaging → Updates); one per open dialog, which posts its result; the one 250 ms supervisor. A command changes the table under its lock and touches the windows only after releasing it, so a window call never waits on a daemon starting.
- `cargo test --manifest-path shell/Cargo.toml` drives the table with stand-in daemons (`cmd` on Windows, `sh` elsewhere) that print a port line and commands, recording what the windows are asked to do instead of opening them.

## Packaging

`npm run installer` builds, on Windows, a per-user NSIS installer (no admin prompt) at `shell/target/release/bundle/nsis/Kanban95_<version>_x64-setup.exe`; on macOS, `Kanban95.app` and a `.dmg` under `shell/target/release/bundle/` (with `--target <triple>`, under `shell/target/<triple>/release/bundle/`):

1. `npm ci` installs the locked dependencies, so a fresh clone or moved checkout builds in one command; then `npm run build` compiles the daemon. Node 24 must be the system Node: `npm.cmd` runs the `node.exe` beside it, so an older system Node stops `npm ci` with `EBADENGINE` whatever is first on PATH.
2. `shell/stage.mjs` copies what the daemon needs at runtime into `shell/target/app/` in the repo's own layout (`daemon/dist`, `daemon/migrations`, `daemon/voice-model.json`, `ui/`, `templates/`, the package files) and runs `npm ci --omit=dev --ignore-scripts` there. It then stages the Node sidecar (below). `--ignore-scripts` is safe on both platforms: node-pty 1.1.0 ships prebuilds for `win32-x64`, `win32-arm64`, `darwin-arm64` and `darwin-x64` in its package, and its install script only checks that the one for this machine exists. On macOS the staged `prebuilds/darwin-*/spawn-helper` is then made executable: the package ships it as mode 644 (node-pty issue #850) and npm keeps that, so every pty spawn fails with `posix_spawnp failed` (`npm run dev` does the same for a dev checkout). The staging holds both Mac prebuilds, so one staging serves the arm64 and the x64 bundle. The workspace link `node_modules/@kanban95` is deleted (a junction, or a symlink on macOS, back to `daemon/` the bundler would walk forever).
3. `tauri build --config shell/tauri.bundle.json` builds the release shell and bundles `target/app/` as the resource `app/`. `shell/tauri.conf.json` keeps `bundle.active: false` so `cargo build` and `npm run dev` stay unbundled. The bundle targets come from the platform files Tauri merges in by itself: `shell/tauri.windows.conf.json` (`nsis`, per-user) and `shell/tauri.macos.conf.json` (`app`, `dmg`; it also merges `shell/Info.macos.plist` into the app's Info.plist for `NSMicrophoneUsageDescription`, without which macOS denies the mic with no prompt). They cannot sit in `tauri.bundle.json`, which is merged last and would give both platforms the same list; Tauri can build NSIS on a Mac host, so `nsis` there would not be skipped.

Installed on macOS, the resource is `Kanban95.app/Contents/Resources/app/` and the exe is in `Contents/MacOS/`, so `daemon_script()` in `shell/src/main.rs` looks in `../Resources/app` as well as next to the exe. An app started from Finder or the Dock gets launchd's PATH (`/usr/bin:/bin:/usr/sbin:/sbin`), without Homebrew's, fnm's or the nodejs.org installer's Node and without the agent CLIs, so on macOS the shell first runs `$SHELL -ilc` (zsh by default) to print the login PATH and appends its entries that are missing (`add_login_path`). Appending keeps a Node 24 already first on PATH in front. A login shell that has not answered in 5 s is killed and PATH stays as it was.

The Mac app is not signed or notarized, so the first launch needs a right-click → Open (README → Install). There are two Mac builds, `aarch64-apple-darwin` (Apple silicon) and `x86_64-apple-darwin` (Intel), each with its own `.dmg` named by architecture (`Kanban95_<version>_aarch64.dmg`, `Kanban95_<version>_x64.dmg`), renamed on the GitHub Release (Releases). A universal build (`--target universal-apple-darwin`) would be one download for both; it is not set up.

**Icons.** `shell/icons/` holds what `bundle.icon` in `shell/tauri.conf.json` lists:
- `32x32.png`
- `128x128.png`
- `128x128@2x.png`
- `icon.png` (512 px, the source for the rest)
- `icon.icns` (macOS)
- `icon.ico` (Windows, the original 32 px icon)

The PNGs and `icon.icns` were made from the 32 px image in `icon.ico`, scaled up with nearest-neighbour so its pixels stay sharp, by `npx tauri icon`. Off Windows the shell will not compile without a PNG in that list: `tauri::generate_context!` takes the window icon from the first `.png`. To change the icon, run `npx tauri icon <new 1024 px png> -o <temp dir>` and copy those files over; the command also writes Windows Store, iOS and Android icons, which the board does not use.

**Node sidecar.** The installer carries its own Node, so the installed app needs no Node on the machine. `NODE_VERSION` at the top of `shell/stage.mjs` names the Node 24 LTS release. For each target, stage.mjs fetches `SHASUMS256.txt` and the official archive for that release from `https://nodejs.org/dist/v<version>/` (`win-x64.zip`, `darwin-arm64.tar.gz`, `darwin-x64.tar.gz`), checks the archive's SHA-256 against the published list, and extracts only the `node` binary to `shell/target/sidecar/node-<target triple>` (`.exe` on Windows), the name Tauri wants for `bundle.externalBin: ["target/sidecar/node"]` in `shell/tauri.bundle.json`. A hash mismatch deletes the download and fails the stage; the old binary is deleted before the check, so a failed stage leaves none (`daemon/test/stage-node.test.ts`). Downloads are cached in `shell/target/node-download/` and a rebuild reuses them, still hash-checked. The target comes from `node shell/stage.mjs [--target] <triple>`; by default it is this machine's, and on macOS both Mac targets, because `npm run installer -- --target <triple>` passes the target only to `tauri build`. Tauri copies the sidecar next to the shell exe as `node.exe` (Windows install dir) or `node` (`Kanban95.app/Contents/MacOS/`). The binary is about 90 MB on Windows.

On Windows, stage.mjs also takes that release's npm from the same archive (`npm`, `npm.cmd`, `npx`, `npx.cmd`, `node_modules/npm`) into `shell/target/npm/`, which `"target/npm/": ""` in `bundle.resources` installs at the install root, beside `node.exe`, the layout nodejs.org ships. It has to sit there: `npm.cmd` runs the `node.exe` in its own folder, and the Git Bash `npm` script loads npm from beside the `node` it runs, so the operator's own npm would run on the operator's own Node whatever is first on PATH. On an older Node that fails `npm ci` for this repo (`engine-strict`, `EBADENGINE`) and every ticket stops at `worktree_setup`. On macOS `shell/target/npm/` is staged empty, which Tauri skips; npm there starts with `#!/usr/bin/env node`, so PATH already picks the sidecar. A missing `shell/target/npm/` fails `tauri build`. The staged npm is npm 11, which skips dependency install scripts it has not been told to allow; node-pty needs none (step 2 above). A Node security release means bumping `NODE_VERSION` and shipping a new app release; the installed app never updates its Node by itself.

Installed, the shell finds `app/daemon/dist/server.js` (next to its exe, or in the bundle's Resources on macOS) and runs it on the `node` next to its exe (`node_exe` in `shell/src/main.rs`), never on a `node` from PATH. Without that file, as in `npm run dev` and `cargo run` (`shell/tauri.conf.json` lists no sidecar), it runs `node` from PATH, which must be Node 24. Agents get the same Node: `childEnv` in `daemon/src/pty.ts` puts `dirname(process.execPath)`, the sidecar's directory, first on their PATH, so `node`, `npm` (installed Windows) and an npm shim such as `codex.cmd` (which runs `node.exe` from its own dir if there, else `node` from PATH) resolve to it; that directory also holds the shell exe, which is harmless. If the sidecar cannot start, the error dialog names the path it tried. The board's repo is the shell's first argument; the Start menu gives none, so the daemon opens the first listed project, or first-run setup on a new machine (Daemon lifetime → Startup without an argument).

**CI.** `.github/workflows/build.yml` runs on every push to any branch (never on a tag push) and on manual dispatch, caching npm and cargo. `release.yml` also calls it (`workflow_call`) with `release: true` (see Releases):

- `windows` (`windows-latest`): `npm ci`, `npm run build`, `npm run test:shell`, `npm run installer`, then lists the setup.exe with `7z l` and fails unless it holds `node.exe`; uploads `shell/target/release/bundle/nsis/*.exe` (and its `.sig` in a release build) as the artifact `kanban95-windows`.
- `macos` (`macos-latest`, Apple silicon): `npm ci`, `npm run build`, `npm run test:shell`, then `npm run installer -- --target <triple> --bundles app,dmg` for `aarch64-apple-darwin` and `x86_64-apple-darwin` (npm appends the args to the `tauri build` call), then checks each `.app` holds an executable `Contents/MacOS/node` of its own architecture (`file`), then a smoke step that spawns `/bin/echo` through node-pty with the arm64 app's own Node from its `Contents/Resources/app` (it fails on a non-executable `spawn-helper`). It uploads every `.app` and `.dmg` under `shell/target/*/release/bundle/` (and in a release build each `Kanban95.app.tar.gz` and its `.sig`) as `kanban95-macos`. CI does not run the daemon's `npm test`: the full suite takes about 12 minutes on a runner and its pty and browser tests time out there, so it is the operator's by hand (`docs/AGENTS.md` → Verification).

### Releases

A GitHub Release is cut only by pushing a tag `vX.Y.Z` (a prerelease such as `v0.2.0-rc.1` works too). Pushes to a branch, `main` included, never release anything.

**Version.** The app version lives in one place: `version` in the root `package.json`. `shell/tauri.conf.json` reads it (`"version": "../package.json"`), the MCP server reports it (`daemon/src/mcp.ts`), and no other file carries one (`daemon/test/version-source.test.ts`). `shell/Cargo.toml` keeps `0.0.0` as a placeholder; Tauri takes the config version over it, so it is never bumped. To release: set `package.json` to the new version (and run `npm install` so `package-lock.json` matches), commit and merge to `main`, then `git tag vX.Y.Z` on that commit and `git push origin vX.Y.Z`. Start → Release board does all of it in one step (`docs/LIFECYCLE.md` → Release board). A test must never hard-code the app version: v1.0.0's release run failed at `npm run test:shell` because a shell test asserted `"current":"0.0.0"`, so shell tests read it from `app.package_info().version`.

**Workflow.** `.github/workflows/release.yml` runs on tags matching `v*`:

1. `version` fails with a clear error unless the tag is `v` + `package.json`'s version, before anything is built.
2. `build` runs `build.yml`'s Windows and macOS jobs with `release: true`, which adds `--config shell/tauri.updater.json` (`bundle.createUpdaterArtifacts: true`) to `npm run installer` and passes the signing secrets to it. The extra config must be a `--config` argument: the Tauri CLI does not read a `TAURI_CONFIG` environment variable for bundling. Tauri then writes a `.sig` next to the NSIS setup.exe (the Windows update bundle is the setup.exe itself) and builds `Kanban95.app.tar.gz` plus `.sig` for each Mac target.
3. `release` checks out the repo (full history, for the previous tag), downloads both artifacts, renames the installers, writes `latest.json` and the release body, and runs `gh release create` for the tag with `--notes-file` (`--prerelease` when the version has a `-`).
4. For a full release (no `-` in the version) it then puts the updater files on the `updater` release: it creates it as a prerelease at the released commit, or else moves the `updater` tag to that commit, uploads with `--clobber`, and deletes every asset not from this version.

The version Release holds only the three installers. Never add another file to it: users take helper files for downloads.
- `Kanban95-<version>-Mac-AppleSilicon.dmg`
- `Kanban95-<version>-Mac-Intel.dmg`
- `Kanban95-<version>-Windows-setup.exe`

Its body is `.github/release-notes.md`, filled by `envsubst` with `${VERSION}`, `${PREV}` (the newest `v*` tag before this one, else the first commit) and the three file names `${WIN}`, `${MAC_ARM}` and `${MAC_INTEL}`. It is the v1.0.2 page: Download, Install, You also need, then the Full Changelog link. GitHub adds the Source code archives itself.

The `updater` release (a prerelease, so GitHub's `latest` skips it) holds:
- `Kanban95_<version>_aarch64.app.tar.gz` and `.sig`
- `Kanban95_<version>_x64-setup.exe` and `.sig` (the Windows update bundle keeps its build name because the signature is over that file)
- `Kanban95_<version>_x64.app.tar.gz` and `.sig`
- `latest.json`

`latest.json` is the Tauri updater plugin's static manifest: `version`, `notes`, `pub_date` and `platforms` with one entry each for `windows-x86_64`, `darwin-aarch64` and `darwin-x86_64`, each a download `url` under `releases/download/updater/` and the `signature` (the content of its `.sig`). `https://github.com/dillon-shearer/Kanban95/releases/download/updater/latest.json` always holds the newest full release; a prerelease version never touches `updater`.

**Signing.** Update bundles are signed with a minisign key pair made once with `npx tauri signer generate`. The public key is `plugins.updater.pubkey` in `shell/tauri.bundle.json`; the app checks every update against it. Any `plugins` entry makes `tauri::generate_context!` emit code that calls `serde_json`, so `shell/Cargo.toml` lists `serde_json` as a direct dependency; without it the installer build fails with `cannot find serde_json in the list of imported crates`. The private key and its password are the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, and the operator keeps the key file offline. They never go in the repo, a ticket, the brain or `~/.kanban95`, and only a release build gets them (branch builds see empty values and make no update bundles). `tauri build` refuses to sign with a key that does not match the public key. Losing the private key means installed apps can never take another update; a new key pair needs a release signed with the old key that ships the new public key. This signature is only for the updater: the installers themselves are not code-signed (Windows SmartScreen and macOS Gatekeeper still warn).

### Updates

The installed app updates itself from the GitHub Releases (Releases above) through `tauri-plugin-updater`, registered in the shell only when it is installed: `staged()` in `shell/src/main.rs` finds the staged daemon next to the exe, the same lookup that picks the daemon to run. `npm run dev` and `cargo run` never check. The plugin's config is in `shell/tauri.bundle.json`, so only installer builds carry it:
- `endpoints`: `https://github.com/dillon-shearer/Kanban95/releases/download/updater/latest.json`
- `pubkey`: the minisign public key (Releases → Signing)
- `dangerousInsecureTransportProtocol: true`, so the override below can be plain http on loopback

`KANBAN95_UPDATE_URL` in the shell's environment replaces the endpoint: an https URL, or `http://127.0.0.1:<port>/...` for a local test manifest; anything else fails the check. To try the dialog on Windows, serve a `latest.json` with a higher `version` from a temp HTTP server and start the installed `Kanban95.exe` with the variable set.

**When it checks.** A daemon under the shell prints `KANBAN95 check=<repo>` right after its port line, unless `updateCheck` in its `settings.json` is false (`askForCheck` in `daemon/src/update.ts`). The shell checks for the first board at shell start and for a daemon back from exit 75 (Restart board) every time; any other `check=` (a board opened later, a crash restart) only if the last check was an hour ago or more. Settings → Board → **Check for updates** prints `checknow=`, which always checks. A check that fails (offline, rate limited) is one `[shell] update check failed: ...` stderr line; the UI hears about it only after the button.

**Shell to daemon.** The shell posts each report to `POST /api/update/shell` on the daemon that asked, with its secret as the `k95` cookie and no `Origin` header (`tell`, plain HTTP over a `TcpStream`). The daemon keeps an `available` offer on the board (`board.update`) and relays every report as an `update` event; the UI shows the dialog from the event or, after a reload, from `GET /api/update`. Later posts `later`, which drops the offer, so the dialog returns only with the next check. The webview still calls no Tauri command: the updater's IPC commands are refused like every other (Network boundary).

**Install.** Update now posts `now`. The daemon refuses it while agents run: the restart hold's tickets to finish plus its open terminals (`docs/LIFECYCLE.md` → Restart after a merge), plus the live agents of other boards this shell hosts (their `running/` entries), since the install closes them too. Else it prints `update=`, and the shell downloads the update it kept from the check (or checks again), posting `downloading` about every 5 percent, then `installing`, then installs:
- Windows: the plugin runs the NSIS setup.exe in passive mode with `/UPDATE` and exits; the installer relaunches the app. The shell's kill-on-close job (Daemon lifetime) would kill the installer with the shell, so the updater's `on_before_exit` first sets `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` on the job (`let_installer_outlive_us`), which starts every later child outside it, then kills the hosted daemons (`Host::shutdown`).
- macOS: the plugin replaces the `.app` and the shell relaunches itself (`app.restart()`).

A download or install that fails is reported as `failed` and shown in the same dialog. On Windows a setup.exe that will not start after the daemons were shut down shows the error dialog and exits the app.

`cargo test` in `shell/` covers the installed/dev decision, when a check runs, the report a finished check sends (a real check against a local `latest.json` and against a closed port), the override's rules, the request `tell` sends, and that a process started after the breakaway is outside the job.

## Network boundary

- `validateConfig` rejects any bind host other than `127.0.0.1`. There is no flag, env var or config key that can widen it; a different host is a code change, and the tests fail on it.
- Every daemon response carries `Content-Security-Policy: default-src 'self' http://127.0.0.1:<port> ws://127.0.0.1:<port>; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; frame-ancestors 'none'` and `X-Content-Type-Options: nosniff`. `data:` images are 98.css's inline SVG icons; `'wasm-unsafe-eval'` lets the speech model's WebAssembly compile (it allows no JavaScript eval); inline styles are for xterm.js, which writes its theme into a `<style>` element. Inline and remote scripts stay blocked, and `connect-src` falls back to the daemon's own HTTP and websocket origin, so the page cannot reach any other host; `frame-ancestors 'none'` keeps other pages from framing it. The window is loaded from the daemon's origin, so this header is the CSP that governs the UI; Tauri's own `app.security.csp` only applies to pages Tauri serves itself, which this app has none of.
- Static serving only answers `GET`/`HEAD`, only for files inside `ui/` with a known extension. Path traversal (`..`, encoded dots, backslashes) resolves outside `ui/` and is refused.
- The webview is an "external" URL to Tauri and the shell declares no capabilities, so every Tauri command is refused for it (tested in `shell/`). The UI talks to the daemon over plain HTTP, the `/events` websocket and a websocket per terminal. The shell cancels navigation off the daemon's origin, sends a new-window request for an https URL to the system browser and drops any other, and answers permission requests itself: microphone yes, everything else no. It also follows the page's fullscreen (Start → Full screen, F11): wry leaves WebView2's `ContainsFullScreenElementChanged` unhandled, so the shell handles it and sets the window borderless fullscreen; without that the page's fullscreen only fills the window. See `SECURITY.md` → Webview.

## REST (operator UI only, same-origin)

Every `/api/*` request needs the `k95` cookie holding the shell secret, or gets `401`; so do the `/events` and `/pty` websockets (`docs/SECURITY.md` → Shell secret).

| method | path | notes |
|---|---|---|
| GET, POST | `/api/tickets` | list / create. Body fields: `title` (required), `body`, `criteria`, `status`, `cli`, `model`, `effort`, `retry`, `needs_human`, `blocked_on_deps`, `blocked`, `depends_on: number[]` |
| GET, PATCH, DELETE | `/api/tickets/:id` | same fields on PATCH; `null` clears `cli`/`model`/`effort`; a PATCH that moves the ticket to `backlog` first ends its live sessions (`runs.outcome` = `reset`, grants revoked, ptys killed); DELETE ends them too and also removes `.kanban95/attachments/<id>/` |
| GET | `/api/tickets/:id/notes` `/audit` | rows for that ticket, oldest first |
| GET | `/api/tickets/:id/runs` | that ticket's runs, oldest first, without `prompt_rendered` and `scrollback`; `has_scrollback` (boolean) says whether output was kept |
| GET | `/api/tickets/:id/runs/:run` | one full run row, `prompt_rendered` and `scrollback` included, for Ticket → Runs and a terminal's end; 404 when the run is not on that ticket |
| GET, POST | `/api/tickets/:id/attachments` | list `[{name, path, size}]` (`path` absolute) / upload: the raw file bytes as the body, its name in `?name=`. | GET, DELETE | `/api/tickets/:id/attachments/:name` | serve / remove one. PNG, JPEG, GIF, WebP and BMP are served inline with their image type; anything else as an `application/octet-stream` download, so an uploaded page never runs on the board's origin |
| GET | `/api/brain?q=&limit=` | FTS5 ranked search (title and tags weigh more than body), limit at most 100; no `q` lists newest. Each row carries `ticket_status`, its source ticket's status (null when none or deleted) |
| GET | `/api/grants` | all grants, never the hash |

## MCP (agents only, bearer grant)

`POST /mcp` is a stateless Streamable HTTP MCP endpoint (no session id, JSON responses). `handleMcp` reads `Authorization: Bearer <token>`, resolves it with `grants.verify`, answers `401` with no audit row when that fails, and otherwise builds a per-request `McpServer` whose twelve tools close over the grant. One wrapper around every tool checks the role cell, runs the handler, and writes exactly one audit row (`ok`, `denied` or `error`) with the grant id and the ticket the call was about. Worker and tester grants are bound to one ticket and may omit `ticket_id`; naming another ticket is a scope denial. Tool list, role matrix and argument tables are in `docs/MCP.md`, generated from the same table the server enforces (`npm run docs:mcp`); a test fails when the file drifts.

## Prompts

1. `startRun(db, repo, {ticketId, template, cli, model, effort, worktree?, base?})` loads `<repo>/.kanban95/templates/<template>.md`. A placeholder outside `VARS` throws here, naming it.
2. `buildContext` reads the ticket, the brain (FTS5 `OR` of the ticket's title and body words, top 8, bodies for the top 2 and an index line for the rest, 2500-char budget cut between rows), the failure notes of the last cycle, the retry count, the base branch, the operator's `preferences.md`, the absolute paths of the ticket's attachments (appended to `{{ticket}}`), the role's tool list from the MCP table, and for a tester `git diff --stat` of the change plus its code diff without markdown, `docs/` and lockfiles, capped at 32 000 characters (`docs/AGENTS.md` → `{{diff}}`).
3. The template is filled in a single pass and the result inserted into `runs.prompt_rendered`. Same ticket and same database give byte-identical output: every query has a total order and nothing reads the clock.

The template is read from disk on every render, so operator edits (by hand or in Settings → Prompts → Templates) apply without a restart.

The copies follow the shipped defaults unless edited. Each copy or reset records the default's sha256 in `<repo>/.kanban95/templates/.shipped.json`. On daemon start (`initTemplates`), a copy whose sha256 still equals its record is unedited, so a changed default replaces it and the record moves on. A copy with no record (written by a daemon from before the record, or under a corrupt `.shipped.json`) is replaced by the default and recorded too, unless it already equals it; its old text goes to `<name>.replaced.md` beside it (git-ignored) and a `[templates]` line on stderr names it, and the next start deletes that file. When git already tracks any of the files a start wrote, the start commits just those files as the operator (`commitPaths` in `git.ts`, "Update the board prompt templates to the shipped defaults"), because a modified tracked file in the main checkout refuses every launch; a repo that tracks none of them (never committed the board's files) gets no commit. Settings → Prompts → Save leaves the record alone, so a copy edited after its record (its sha256 matches neither the record nor the default) is never overwritten. `GET /api/templates` marks any copy that differs from the current default `stale`, and Settings → Prompts shows it next to Reset. Template-to-role and template-to-phase mapping is the `TEMPLATES` table in `templates.ts`; agent-facing behaviour is in `docs/AGENTS.md`.

## Launch

`launch({ db, repo, port }, { ticketId, template, cli, model, effort })` in `daemon/src/launcher.ts`, also exposed as `start().launch(...)`. In order:

1. `createWorktree` → `<board home>/worktrees/<repo key>/t-<id>` (`worktreePath` in `daemon/src/git.ts`; the board home is `$KANBAN95_HOME` or `~/.kanban95`, the repo key the repo folder's name, a dash and the FNV-1a hash of its canonical path, so two repos with the same name never share a root) on `ticket/<id>` from the repo's current branch, reused if it exists; refused if the base branch has uncommitted tracked changes. Never under the repo: in a synced folder (OneDrive) every worktree's `npm ci` was uploaded, the account was throttled, and locked files made worktrees impossible to remove. A ticket whose branch is still checked out where an older board put it, under the repo, has that worktree moved here (`git worktree move`) with its work.
2. `startRun` renders the template and inserts the `runs` row (a bad template stops here, nothing is minted).
3. `mint` a grant with the template's role (`TEMPLATES[template].role`).
4. Session dir `.kanban95/sessions/<run-id>/`, owner-only, with `prompt.md` and (Claude Code) `mcp.json`, plus `settings.json` for a Claude worker or tester (`docs/CLIS.md`).
5. `buildArgv` with the role (flags and reach per role in `docs/CLIS.md`); for Claude Code, `preTrustClaude` makes sure the repo's worktrees root is trusted; then `spawnPty` with `cwd` = worktree and the env allowlist.
6. The session is kept in `sessions` (by run id) until its pty exits. On exit, for any reason: `runs.ended_at` and `runs.scrollback` are written, the grant is revoked, the session dir is removed, the lifecycle's exit hook runs (`runs.outcome`, and the `exit` event if the agent never reported), `session.done` resolves.

The lifecycle owns Launch: `POST /api/tickets/:id/launch` and the transitions after it call `launch` with the run settings from `~/.kanban95/models.json` (and the CLI path from `settings.json`, when set).

A **brainstorm** (`POST /api/brainstorm`) and an **operator terminal** (`POST /api/operator`) share steps 3 to 6 through one function, `launchRoot`, but have no ticket: no worktree, no `runs` row, a grant with no ticket, `cwd` = the repo root. A brainstorm runs on the plan-phase settings; an operator terminal on the operator phase (the CLI's own default model when that has none). A brainstorm runs the `brainstorm.md` brief on a planner grant (no file writes). An operator terminal runs `operator.md` with the operator's typed `{{mission}}` on an `operator` grant: the worker's CLI flags (permissions off, no sandbox, as the operator's account), and over MCP what the operator could do by hand on the board (every planner tool, plus editing, moving, noting and re-modelling any ticket; never `ask_operator` or `report_test`). It only starts from the operator's click in the UI, `.kanban95/config.json` `operator` overrides its model and effort when set, and its grant is revoked when its pty exits (X on its window ends it after a confirm), like every session's (`docs/SECURITY.md` → Operator terminal). Either one's session key is minus its grant id (there is no run id), so its session dir is `.kanban95/sessions/-<grant>/` and its terminal `/pty/-<grant>`. A session dir is owner-only when it holds a bearer (Claude Code's `mcp.json`); a Codex session's dir holds only `prompt.md`, which Codex's read-only sandbox (another Windows account) must be able to read.

Any failure after the run row is written revokes the grant and removes the session dir before the error is rethrown. Revoking the grant over REST kills the pty, which runs the same teardown. `close()` stops new spawns, kills every live pty, waits for their teardown and for the merge queue to drain, then closes the database. On start the daemon runs the janitor sweep and the lifecycle's recovery (`docs/LIFECYCLE.md` → Restart), and the sweep again every 24 hours.

### Terminal websocket

`/pty/<key>` (the run id, or minus the grant id for a brainstorm or operator terminal) with a websocket upgrade, same-origin only. The server first sends the scrollback so far, then every pty output chunk as a text frame, and closes when the pty exits. The client sends JSON: `{"data": "..."}` is written to the pty as typed input, `{"resize": [cols, rows]}` resizes it (1 to 999 each). Anything else is ignored. A frame over 64 KiB, or any other protocol error, closes only that connection; the UI sends a long paste as several `data` frames of at most 8192 characters each. Several clients may watch one run.

## Events

`/events` is a same-origin websocket that only sends. `{"sound": "ding" | "chord" | "done", "ticket": n}` when a ticket merges, needs the operator, or passes its test and lands in Done (`done`, sent by the `pass` transition before the merge queue takes the ticket; a `ding` with `ticket: null` when the runner stops itself); `{"ticket": n}` whenever something about ticket `n` changed (any lifecycle transition, an operator REST mutation, an agent's successful MCP call, a session of that ticket ending); `{"ticket": null}` when the set of live sessions changed without a ticket (a brainstorm or operator terminal started or ended) or the runner changed. `{"update": {"state": ...}}` relays a report of the shell's updater (Packaging → Updates). `{"type": "pick", "token": "...", "path": "..."}`, or `"cancelled": true` in place of `path`, is the result of the dialog `POST /api/pick` asked for, also sent as cancelled when nobody answered within 5 minutes. `{"type": "open-failed", "folder": "...", "reason": "..."}` is the shell's report that a board this one asked it to open did not start (the reason on one line); the status bar shows it. The UI never polls the board: it refetches what an event names.

## UI

`ui/`, plain ES modules, no build step. How to use it: `docs/OPERATOR.md`.

Boot (`boot` in `app.js`) runs in two stages, on every launch and every board switch (a switch reloads the page):
- First paint waits only on `GET /api/tickets`, `ui.json` (window places, startup layout) and settings (zoom, tiling). It then opens the startup layout windows, so the Board shows its cards, and logs `First paint: <n> ms` to the console.
- Everything else trickles in after and updates in place: `GET /api/update` (version in the Start menu, Release board, the update offer dialog), models (cards show `no model` and `cli?` until they land, then redraw), `refreshShared` (sessions, inbox, runner), then the Ready check. The project list (Ctrl+Tab, Start → Projects) and limits were never awaited.

- `icons/`: the desktop and taskbar icons, self-drawn 32x32 SVGs (the taskbar shows them at 16px) served from the daemon's origin (`img-src 'self'`). The wallpaper is CSS gradients in `app.css`, no image, over a base colour in `--k95-wall` on `body` (default teal): `app.js` sets it from `GET /api/project` at boot and after Settings → Projects saves, and sets `document.title` to `<folder name> — Kanban95`. Tauri 2 does not copy `document.title` to the OS window, so the shell titles its window the same from its repo argument (`title()` in `shell/src/main.rs`).
- `wm.js`: the window manager.
  - Windows are 98.css `.window`s positioned on `#desktop`, dragged by the title bar (pointer events), resized by CSS (`resize: both`), minimized to a taskbar button, maximized to fill `#desktop` (the `max` class overrides the inline geometry, which stays as the restore geometry; drag and resize are off), clamped so a title bar is always reachable.
  - The taskbar is modern Windows in Win95 dress: after Start, `#pinned` holds one-click launchers for the desktop icons' entries (Quick Launch; built by `desktopIcons()` in `app.js`), then `#tasks` holds one button per open window, its icon then a short label in a 10px font, 80px wide with the label cut by an ellipsis; the tray (Switch board, Inbox n, Restart, the limit, the agent count, the clock) uses the same 10px font with tight padding (the pinned launchers stay icon-only). Switch board (`#switch`, an inline SVG in `index.html`) opens `openSwitch()` in `app.js`: it refetches `GET /api/projects`, builds a `.k95-switch` panel of the other projects above the button, and removes it on close; nothing polls while it is closed. `open()`'s `icon` names the button's picture (`icons/<icon>.svg`, default `window`): `board`, `inbox`, `brain`, `settings`, `notepad`, `limits`, `ticket`, and for terminals `termIcon(s)` in `app.js` (`execute`, `test`, `brainstorm` for a brainstorm or a plan phase, `operator`). `open()`'s `label` is the button's text, default the title (Board, Ticket #12, New ticket, …); terminals pass `termLabel(s)` (`#74 execute`, `Brainstorm`, `Operator`). `api.title(text, label)` changes both, the label defaulting to the new title; an ended terminal's gets " (ended)". The full title is the button's tooltip and `aria-label`. Past the bar's width `#tasks` scrolls (arrow buttons at its ends and the mouse wheel), and focusing a window scrolls its button into view. Each button has a menu (right-click, Shift+F10, Menu key; `open()`'s `items` add entries, such as a terminal's Open ticket), a Ctrl/Shift+click selection whose menu acts on every selected window, and pointer drag to reorder (session only, not saved).
  - Windows opened with `persist` (Board, Brain, Inbox, Settings, Notepad) keep position, size and maximized state in `.kanban95/ui.json` (through `state.js`) as `k95.win.<window id>`, with the desktop size in screen px it was saved at (`dw`, `dh`; the startup layout's entries carry them too): `open` scales a saved place to the current desktop.
  - On a window `resize` (the shell's window, full screen) every window's inline geometry is scaled by the change in desktop size, so nothing leaves a bar of empty desktop; screen px, not CSS px, so a zoom change is not a resize.
  - Windows opened with `tile` (every terminal) take a slot instead, and the grid always fits: `retile()` packs the members (tiled, shown: not hidden, not `max`, and not `free`) into slots 0..n-1, numbered in reading order, sorted by the `slot` each last held (a window coming back to a slot goes ahead of the one `packed` into it meanwhile, so restore puts it back) with new ones (`slot: null`) last, up to the last `SLOTS` count, 12. A minimized or maximized window keeps its old `slot` number only as its sort key. The grid is the first `SLOTS` row (`[up to n, columns, rows]`: 1 → 1×1, 2 → 2×1, 3 → 3×1, 4 → 2×2, 6 → 3×2, 8 → 4×2, 9 → 3×3, 12 → 4×3) whose n covers the member count. The last row stretches: its members share the full region width (5 is 3 + 2 halves, 7 is 4 + 3 thirds), so there is never a hole. The region runs from 4 px right of the desktop icons (`#icons`, so a terminal never covers an icon) to the left edge of the leftmost shown `ACTION` window (Board, Inbox, Notepad), full height; to the desktop's right edge when none is shown or the region is under `MIN_REGION` px. A tiled window whose geometry changed between pointerdown and pointerup (dragged or resized, not maximized) is free (`slot: null, free: true`): it stays where it was left and `place()` is not involved; a title-bar double-click on a free, non-maximized window clears `free` and re-tiles, so it joins the grid last (on any other window, or with tiling off, the double-click maximizes). `setTiling(false)` (Settings → Board, `terminals.tile`, applied at boot) makes `retile()` do nothing: terminals open at `place()` and stay where dragged; `setTiling(true)` clears `free` on every window and retiles at once, so every terminal joins the grid. `retile()` runs (debounced 50 ms) when a tiled or action window opens, closes, is minimized, restored, maximized, dragged or let go, on a desktop resize and on a zoom change; a 13th terminal opens at `place()` and joins when a member leaves. Ended terminals stay members until closed (Start → Close ended terminals in `app.js`). To change the arrangement edit `SLOTS` (and `ACTION`).
  - A window with nothing saved and no `tile` opens at `place()`: of the desktop corners and a half-window grid, the spot overlapping the least area of the open, non-minimized windows (top-most, then left-most on a tie).
  - `raise(id)` brings a window to the front, out of minimized, without making it the focused one: a terminal whose state turns `human` (its ticket needs the operator) is raised.
  - `snapshot(ids)` returns the open windows among `ids` with that geometry, bottom-most first: `app.js` builds the startup layout on these (`k95.layout` in `ui.json`, which says which windows `boot` opens; `seed(key, r)` gives each its layout place for that one `open`, used only when the window has no remembered place and never saved, so a window the operator moved opens at its own place and an unmoved one follows the layout; no stored layout means `defaultLayout()`, the action column: Board top right, Inbox bottom right and Notepad left of the Inbox at its height, half the desktop's width together, sized from the desktop at every start and clear of the desktop icons; Reset `forget`s the layout windows' places).
  - A window's place is saved only when its geometry changed, so a click inside an unmoved window does not pin it.
  - Also modal dialogs (`<dialog>`) and pop-up menus.
  - `setZoom(f)` sets the UI zoom (`settings.json` `zoom`, Ctrl+=/−/0 in `app.js`) as CSS `zoom` on `body`, so dialogs and menus appended to it scale too, and re-clamps every window. Inside the zoom, offsets, inline styles and saved geometry are CSS px before zoom, while `clientX`/`clientY` and `box(el)` are screen px: divide those by `scale()` before writing them to a style (drag, menus, the card ghost, the Start menu). `box(el)` is `getBoundingClientRect` in screen px on every engine (see Working on the board). `menu(x, y)` keeps the menu inside `#desktop`, so it never covers the taskbar. xterm measures its cells after zoom, so terminals keep their `fontSize` and only refit.
- `app.js`: the data layer and every window.
  - It loads tickets, sessions, the Inbox and both settings files once, then listens on `/events`. Frames are coalesced: each `{ticket}` frame marks that ticket dirty, and about 50 ms later one pass refetches every dirty ticket once, then the live sessions, the Inbox and the runner once, and asks each open window to redraw once with the set of changed ids; a frame that arrives during a pass queues one trailing pass. Sound frames still play and speak per frame. Each window decides whether the pass concerns it (a ticket window only when its own ticket is in the set; form tabs never, so typing is not lost).
  - A new session opens its terminal window automatically, behind the focused window; a terminal whose run the board ended (`submit`, `pass`, `fail`, or `conflict` and `restart`, which start a new run of the same ticket) closes itself after a moment; one the agent exited on its own, or that was revoked or died, stays open, marked ended.
  - When `refreshTicket` finds a ticket in Backlog it closes all of that ticket's terminals, ended or not: a reset stopped its agents. Add any new lifecycle event that runs `end_session` to that list in `openTerminal`, or its stale window will sit in front of the new run and the ticket will look stuck.
  - A terminal's title bar is coloured by `termState(s, ended)` in `app.js`, first match wins: ended, the ticket's `needs_human`, then brainstorm/operator, then the phase. It sets `data-state` on the window; the palette is the `.k95-win[data-state=…]` rules in `app.css`, whose unfocused (`.inactive`) gradient is the same two colours mixed toward grey. `refreshTicket` repaints that ticket's open terminals, so a flag recolours them in place.
- Board drag uses pointer events, not HTML5 drag and drop. A card can be dropped into any column, as an operator move (`docs/LIFECYCLE.md` → Moves by hand). When the ticket has a live agent, the drop asks for confirmation first, and the daemon then stops the agent; a move to Backlog also clears flags and retries and closes the ticket's terminal windows. A move by hand starts no agent. Clicking a column's legend folds it to a 24px strip (label and count vertical, no cards; the grid's `grid-template-columns` gives the others the width). A strip keeps `data-status`, so drops onto it work; its count turns red when it holds a needs-human ticket. The folded set is `k95.collapsed` in `.kanban95/ui.json`; with nothing saved, Done starts folded (a saved empty set unfolds it).
- The Board's Filter and per-column Sort (`view` in `ui/app.js`, `k95.view` in `.kanban95/ui.json` as `{ filter, sort: { backlog, in_progress, testing, done } }`) only change what a redraw shows: `shown(t)` decides a card, `sorted(list, key)` orders one column by its own `SORTS` key (ties by id). The Filter box sits at the right end of the Board's toolbar; each column's sort is picked from the ▾ on its legend (`sortPick`, a `wm.menu`; it stops the click so the legend does not fold), and a sort other than id shows in the legend ("Done (86) · updated"). `loadView` reads the saved value: an old single sort string applies to all four columns, an old `group` is ignored. A card the filter hides or a folded column holds is out of the selection (`picked()` drops it, Ctrl+A skips it), and Shift+click ranges follow each column's drawn order (`order`).
- `requirements.js`: the Requirements list and its Check again button, shared by `setup.js` and Settings → Agents in `app.js`; its links use `target=_blank`, which the shell opens in the system browser.
- `state.js`: the UI's state across restarts, `.kanban95/ui.json` via `GET`/`PUT /api/ui`. `load()` once in `boot` before any window opens, then `get`/`set` on an in-memory object; a `set` writes the whole object 500 ms after the last change, and a pending write is flushed (`keepalive` fetch) on `pagehide`. Nothing in `ui/` uses browser storage: the daemon's port, so the page's origin, changes every start.
- `voice.js`: the mic button and `transcribe(blob)` (see Voice).

Vendored from npm, no CDN: 98.css 0.1.21; `@xterm/xterm` 6.0.0 and `@xterm/addon-fit` 0.11.0 (`xterm.mjs`, `addon-fit.mjs`, `xterm.css`); `@huggingface/transformers` 4.3.0 (`transformers.min.js`, which bundles the ONNX runtime's JavaScript) with the matching `onnxruntime-web` 1.31.0-dev.20260914 WebAssembly runtime (`ort-wasm-simd-threaded.asyncify.{mjs,wasm}`, 27 MB, used for both WebGPU and WASM). ## Voice

A mic button sits beside every text field (added by a `MutationObserver`, so new windows get one too; fields marked `data-mic="off"`, such as model ids and paths, do not) and in every terminal's title bar. Push to talk by default, click-to-toggle in Settings. A button runs one start at a time: release, pointer cancel or a second click while the model check or microphone permission is still pending cancels it, and a stream that arrives after that is stopped at once. Removing the button from the page stops its recorder and tracks without transcribing. `MediaRecorder` records; `transcribe(blob)` dispatches on the configured backend, of which `local` is the only one: transformers.js runs `automatic-speech-recognition` with the pinned Whisper model, on WebGPU when the webview has an adapter and WASM otherwise, after `AudioContext` decodes the audio to 16 kHz mono. Text goes to the field's caret, or to the pty as `{data}` without Enter. A daemon-side or provider backend would be another entry in `voice.js`'s `backends` table; nothing else changes.

The model is pinned in `daemon/voice-model.json`: `onnx-community/whisper-base.en` at one Hugging Face revision, seven files (configs, tokenizer, q8 encoder and merged decoder, 79.6 MB), each with size and SHA-256. The UI shows that manifest before anything is fetched; on OK, `POST /api/voice/download` fetches each file from `<source>/resolve/<revision>/<path>`, refuses more bytes than pinned, checks size and hash, and renames it into `~/.kanban95/models/whisper-base.en/`; a mismatch deletes the file and fails the download. Every board shares that folder, so a download holds `whisper-base.en.lock` (a SQLite write transaction, polled every 200 ms by a waiting board and dropped by the OS if the holder dies) and stages each file in its own `<file>.<pid>-<uuid>.part`. A board that waited finds the files verified and fetches nothing; a part file found under the lock was left by a dead attempt and is deleted. A failure deletes only that attempt's part file, and a file appears under its real name only by rename after its hash checks, so the UI never loads a partial file. transformers.js is set to local models only (`/voice-model/<id>/…`, which serves manifest-listed files and nothing else), no browser cache, and no WASM preload cache (its preload imports the runtime from a `blob:` URL, which the CSP refuses).

Checked on Windows 11, WebView2 154 inside the Tauri window: `navigator.gpu` gives an adapter and the model runs on **WebGPU**; a recorded sentence transcribes correctly, about 7 s for the first call (model load included) and 3 s after. In headless Edge (no adapter) it runs on WASM.

Checked on macOS 15.5 (Intel), system WKWebView: `navigator.gpu` gives no adapter, so it runs on **WASM**; the WAV fixture (`merge-queue.wav`, removed from `daemon/test/fixtures/` in ae21189, still in git history) transcribes as "Please add a test for the merge queue.", about 16 s for the first call (model load included) and 3 s after. The download into a data folder on an exFAT drive verifies and renames as on Windows.

## Working on the board

Gotchas collected while the board was built. Each one cost a phase some time.

**Node and the daemon**
- Agents need no Node setup: their pty `PATH` starts with the daemon's Node 24, and a new worktree has already run `npm ci` (`worktree_setup`, `docs/LIFECYCLE.md` → Worktree setup). Run `npm run test:changed` in the worktree as it is. Never junction main's `node_modules` into a worktree.
- Outside the board, `node` on PATH may still be an older Node. On Node 22 `import.meta.main` is `undefined`, so the daemon prints nothing and the shell fails with `bad daemon handshake ""`, and tests fail with `no such module: fts5`. `npm run dev` needs Node 24 first on PATH; in a bare shell run `fnm env --use-on-cd | Out-String | Invoke-Expression` first, or put the Node 24 install dir first on PATH. `fnm exec` cannot start `npm` (a `.cmd` shim), and Node 24 throws on `process.exit(true)`.
- The daemon's first stdout line is the handshake. Anything printed before it breaks the shell; log to stderr. After it, a stdout line starting `KANBAN95 open=`, `switch=`, `popout=`, `dock=`, `close=`, `restart=`, `check=`, `checknow=`, `update=` or `pick=` is a command to the shell (Hosted boards). Only `tellShell()` in `daemon/src/boards.ts` writes those; nothing else in `daemon/src` writes to stdout (`console.log`, `process.stdout`), and `daemon/test/shell-commands.test.ts` checks it.
- A daemon started with stdin closed exits right after printing its port (Daemon lifetime). Spawn it with a held-open stdin pipe.
- `DatabaseSync.exec` with several statements leaves a transaction open if a middle one throws. `migrate` and `api.ts`'s `transaction()` use explicit `BEGIN` / `COMMIT` / `ROLLBACK`; do the same anywhere else.
- `audit.ticket_id` is a foreign key: attributing an audit row to a ticket that does not exist throws. Check existence or pass `null`.
- `apply` is synchronous and may spawn agents (`execFileSync git`, a pty) inside an MCP request. Effects run after the transaction commits, so a failing effect (a launch) re-enters `apply` with `exit`.
- With the runner off (no `runner.json`, the default in tests) the board starts no agent by itself: a held dependent stays held when its dependency merges and a conflict below the retry cap waits with no agent (`apply`'s `auto`, docs/LIFECYCLE.md → Stop holds every automatic launch). A test that expects either to run on its own must turn the runner on, and keep something running (a `hang` ticket) if a flagged ticket would otherwise let it stop itself.
- `sessions` in `launcher.ts` is module-level, shared by every `start()` in one process: one daemon per process.
- Every session the board ends, and a `worktree_setup` that overruns its timeout or is cancelled (`cancelSetup`), is killed through `killTree` in `launcher.ts`; never call `pty.kill()` or `child.kill()` directly. `pty.kill()` alone ends the `cmd.exe` that `spawnPty` wraps around the CLI and whatever is attached to its console, and leaves grandchildren without one (headless Edge, detached workers, an MCP server, `npm`) running: the operator's machine once filled with orphaned `node.exe` and Claude Code processes. `killTree` runs `taskkill /T /F /PID <pid>` on Windows (it walks the tree by parent pid, so it must start while the root is alive; it runs asynchronously, so a slow taskkill under load does not stall the daemon) and kills the process group on POSIX (node-pty starts the child with `setsid`; `prepareWorktree` spawns detached on POSIX for the same reason), then calls `kill()` so node-pty still reports the exit. On Windows it calls `kill()` only if taskkill timed out, while the root is still alive: node-pty reports a dead root's exit by itself, and its `kill()` forks a helper that lists the console of the root's pid after node-pty has let go of it and kills every process there, so a reused pid on another console takes that console's processes with it. It killed vitest twice and, with the suite run from an agent's terminal, the agent itself; checking first that the pid is alive does not help, as a reused pid is alive. A session goes through `killSession`, which adds one step on Windows: a kill before the CLI printed any visible text can land while `cmd.exe` is still starting it (under load that takes up to a second), and the CLI created after taskkill's snapshot runs on, orphaned; so once node-pty reports the root's exit, however late, one PowerShell sweep (1-5 s, and `done` waits for it) kills every process whose parent was the root and that started after the session and before the pid's current owner, if the pid was reused. Under load each taskkill takes seconds and they queue, so the sweep must not give up on a root that is slow to die: a 5 s cap once skipped it exactly when the race is most common. `daemon/test/kill-tree.test.ts` checks a grandchild dies on each path and that a CLI killed while starting is gone.
- A merge that touches `daemon/` or `shell/` takes effect only after a board restart (`npm run dev` rebuilds); `ui/` changes show at once.

**MCP**
- `TOOLS` in `mcp.ts` is the only place a tool is defined. After changing its `access` or `description`, run `npm run docs:mcp` or the doc test fails. `MOVE_TARGETS` and `WORKER_FIELDS` feed both enforcement and the matrix text. A worker or tester grant's reach beyond its role cell (its ticket's `agent_level` and `read_all`) is worked out only in `reach()`; its ticket's `targets` widen only `get_ticket`, `list_tickets` (`readable()`) and `update_ticket` (`editTarget()`), which sets `Call.as`; a tool's `run` checks `c.as`, never `c.grant.role`, for what it allows, or a level stops widening it.
- A handler refuses by throwing the module-private `Deny`; anything else thrown is audited as `error` and its message goes back to the agent verbatim.
- `enableJsonResponse: true` returns each tool result as one JSON body. A tool that needs progress notifications would need that switched off for its server.
- The MCP SDK pulls in express, hono and ajv transitively. Nothing imports them; `node:http` is the only server.

**Templates**
- Operator edits to `<repo>/.kanban95/templates/` survive restarts. A changed default in `templates/` reaches a repo's copy on the next daemon start if the copy is unedited or has no `.shipped.json` record (Prompts above); a copy edited after its record stays and shows as differing in Settings → Prompts, where Reset brings it back in step. A template that adds a `{{var}}` reaches copies only after the board restarts on the build that knows it, which is the order this gives for free.
- Running the daemon on this repo creates `./.kanban95/templates/` (untracked, not ignored: in a target repo they are meant to be committed).

**Windows**
- node-pty 1.1's Windows `kill()` closes the pseudoconsole, then forks a helper to list the console's processes, which fails (`Error: AttachConsole failed` on stderr); 5 s later it `process.kill`s the shell's pid, which has exited by then and which Windows may have reused, so under a full `npm test` it ended other agents and git mid-merge. `spawnPty` (`daemon/src/pty.ts`) replaces that list with an empty one; `killTree` ends the tree itself. When the shell exits, node-pty drops its pseudoconsole handle without closing it (`ClosePseudoConsole` runs only in `kill()`, and node-pty forgets the handle before it reports the exit, so a later `kill()` cannot close it either), so each session's `conhost.exe` stayed a child of the daemon until the daemon exited. `spawnPty` closes conhost on node-pty's exit event by destroying its end of the console's input pipe (`_agent._inSocket`): conhost exits on the broken pipe. The exit event comes after node-pty's output flush, so no output is lost; `daemon/test/conhost.test.ts` checks it. A bare `kill()` only closes the console, which under load left the shell and the CLI running and their repo locked: a test, too, waits for the fake's first line and ends a session with `killTree(s.pty)`. A one-off script using node-pty gets the stray kill unless it does the same. `useConptyDll: true` avoids the helper at about 3 s per spawn, so it is off. A one-off node script using node-pty does not exit by itself after the pty ends: call `process.exit`.
- node-pty 1.1 on Windows has two sockets with no 'error' listener, and an error on either is an uncaught exception (vitest: "Unhandled Errors", exit 1 with every test passed). The console input socket (`_agent._inSocket`) fails with EPIPE when written after conhost is gone. The conout worker thread (`node-pty/lib/worker/conoutSocketWorker.js`) pipes the console output into a socket whose other end is node-pty's `_outSocket`; when that end closes while the console still prints, the worker's socket fails with EPIPE ("write EPIPE", or "This socket has been ended by the other party" when the close lands between its end and finish), the worker dies and its `Worker` emits 'error' in the daemon. `spawnPty` attaches a no-op listener to both; `daemon/test/pty-conout-epipe.test.ts` checks the worker case.
- A test must close its database before `rmSync`, or it gets `EPERM`.
- A directory an agent ran in stays locked for seconds after its pty exits when the machine is loaded (a full `npm test` beside other boards' agents): `rmSync`'s default retries (5 × 100 ms) end in `EPERM`. A test removes its temp dirs, and `test/home.ts` the test home that holds the agents' worktrees, with `removeTemp` (`test/home.ts`): it retries about 7 s, then warns and leaves the dir in the run's `k95-run-*` temp dir instead of failing the file. The run's teardown (`test/real-home-guard.ts`) removes the whole `k95-run-*` dir after every worker ended, first killing and listing (`killed processes this run left running`) any process whose command line names the run dir, such as a fake agent orphaned by a kill; the daemon's `cleanTicket` retries about ten seconds. A fake agent can also take over 5 s to print its first line then: wait up to 20 s for it. The pty files' `until` (`test/board.ts`) waits 30 s by default: a merge in `lifecycle-merge.test.ts` measured 12 s alone on macOS, and a wait past 30 s is a failure, not load.
- On a loaded machine (2026-10-11, Windows 11, a `--project pty` run from a board agent's terminal beside other boards' agents, 450-700 processes) Windows now and then refuses to start a process: it exits at once with `0xC0000142` (STATUS_DLL_INIT_FAILED; node-pty reports `-1073741502`, `execFileSync` `status: 3221225794`). That, not a slow fake, is the fake agent that "prints nothing for 20 s": its terminal shows only ConPTY's opening `[?9001h[?1004h` and its pty has exited. Measured over 15 runs, every fake that did start printed within 100 ms of its node starting. The same failure hit the merge queue's git (a merge lost, so "timed out waiting for … merged") and vitest's own workers ("Worker exited unexpectedly with exit code 3221225794"). The board starts such an agent or merge job again (`START_RETRY`, `docs/LIFECYCLE.md` → Processes that never started); a failed test that shows this code in a worker crash is load, not your change. To find it next time: log `exitCode` in `spawnPty`'s `onExit` and the `[merge]` errors' `status`/`code`.
- The repo is LF (`.gitattributes`), except `.cmd` files, which are CRLF because cmd.exe misreads labels with LF. Python on Windows writes CRLF in text mode: open files with `newline=''` when scripting edits.
- The suite runs on Windows and macOS. A test that puts a stand-in agent CLI on PATH writes it with `fakeCli(bin, name, script)` (`daemon/test/fake-cli.ts`): a `<name>.cmd` for cmd.exe and an executable `<name>` shell script, both running `node <script>` from the same dir. A `.cmd` alone leaves macOS with no `claude` on PATH and every pty spawn fails with `posix_spawnp failed`, which used to show up as a 30-100 s timeout. `fakeCli` now runs the stand-in once with `K95_PROBE=1` (the shim then runs `node --check` on its script) and throws `stand-in CLI <name> cannot start: <cause>` within 5 s when that fails (`test/fake-cli.test.ts`). `daemon/vitest.config.ts` drops PATH entries that do not exist: npm adds about nine missing `node_modules/.bin` dirs, and on macOS every spawn by name tried each one, which made a git call 10-20 times slower. Read the test home from `process.env.HOME` or `USERPROFILE`: `test/home.ts` sets both. `daemon/vitest.config.ts` makes node-pty's `spawn-helper` executable on macOS (it ships as mode 644, node-pty issue #850), and `test/cdp.ts` finds Chrome or Edge under `/Applications`.
- A unit test that awaits the janitor's `sweep` also waits for `sweepProcesses`, a PowerShell `Get-CimInstance Win32_Process` listing (`ps` on macOS) that takes about 3 s idle and over 20 s in a loaded parallel `test:changed` run. A test that is not about orphan processes mocks `node:child_process` `execFile` to call back with empty output (`test/janitor-reopened.test.ts`); git runs through `execFileSync`, so the real git work still happens. Tests that do several git calls or start a daemon set a 20 s timeout; vitest's 5 s default does not hold under load.
- A stale `shell/target` from another checkout path fails the Tauri build reading permission files; `cargo clean` fixes it.
- Do not redirect `USERPROFILE` for the Tauri shell: WebView2 fails to start. Killing the shell with `kill()` alone can leave `msedgewebview2.exe` children; the job object (Daemon lifetime) handles a normal exit.
- Probing a second shell beside a live board: set `KANBAN95_HOME` to a scratch dir (or the probe's repo lands in the operator's `projects.json`) and `WEBVIEW2_USER_DATA_FOLDER` to another (else the probe gets its own per-repo profile under `%LOCALAPPDATA%`, see Daemon lifetime, to delete afterwards), find your processes by walking `ParentProcessId` from your shell's pid, and kill only those, never by name. `taskkill /F /PID <shell>` without `/T` is enough. `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<n>` exposes the webview to DevTools (`http://127.0.0.1:<n>/json/list`).
- `cargo run` / `cargo build` of the shell always relinks `kanban95-shell.exe`: tauri-build tells cargo to watch `shell/capabilities`, which does not exist (on purpose), and a missing watched path reruns the build script every time. On Windows the relink fails with `Access is denied` while any board runs from that exe, so a second `npm run dev` from the same checkout fails; Start → Projects starts the built exe directly instead.
- Shell tests stand in for a daemon with a `cmd` line (`tests::host` in `shell/src/main.rs`). Pass it with `raw_arg`, not `args`, so Rust's quoting does not change it; `findstr x` holds it open until stdin EOF, as a daemon waits; and write an env var to a file as `>"file" echo %VAR%`, because in `echo 1234>file` cmd takes the digit before `>` as a handle number. Killing the `cmd` leaves `findstr` running until the test drops the child's stdin, so stop stand-ins through `Host::shutdown` or `close=`.
- A process started by the daemon stays in its shell's kill-on-close job, also with `detached: true`. To outlive the board, create it through WMI (`boards.ts` `startDetached`); it gets a fresh environment unless one is passed in `Win32_ProcessStartup.EnvironmentVariables`.
- The same job would kill the update installer the shell starts (`ShellExecuteW` in tauri-plugin-updater) when the shell exits a moment later. `let_installer_outlive_us` in `shell/src/main.rs` sets silent breakaway on the job just before; anything that has to outlive the shell needs the same (Packaging → Updates).
- In PowerShell, `$null` passed to a P/Invoke `string` parameter arrives as `""`: `FindWindowW($null, title)` looks for a class named `""` and finds nothing. Pass `[NullString]::Value`.
- Never rebuild or run the installer while the operator's board is live: a rebuild replaces `daemon/dist` under the running daemon, and NSIS closes the app. Test on a second instance.

**A repo on a carried drive (macOS)**
- On a volume that is not APFS or HFS (an exFAT SSD shared with Windows), macOS writes an AppleDouble sidecar `._<name>` beside every file and a `.DS_Store` in folders. `.gitignore` lists `._*` and `.DS_Store`, so they never show as untracked and `git add -A` never stages them. A `._*` file inside `.git/objects/pack` makes git fail with `non-monotonic index`; delete `.git/objects/pack/._*` (or run `dot_clean` on the repo).
- exFAT keeps no file modes, so after a checkout made on Windows every file can show as modified. On start on macOS, `guardFileMode` (`git.ts`) reads the volume type (`df -P` then `diskutil info`) and sets `core.fileMode false` in the repo when it is unset and the volume is not APFS or HFS, with one stderr line. It does nothing on Windows or Linux and never overrides a value already set. Tests pass the volume check in as an argument.
- A tracked file missing from the working tree blocks every launch (`createWorktree` refuses a dirty base). The refusal counts the changes by kind and names the restore command: `git checkout -- <paths>` for up to 10 unstaged paths, `git checkout -- .` above that.
- On Windows, git refuses a repo on exFAT as "dubious ownership" (the volume records no owner) and the board used to stop with `launch failed: no git repo with a commit ... safe.directory`. `initRepo` now calls `trustUnownedVolume` (`git.ts`), which trusts it for the board's git and its agents only (`docs/SECURITY.md` → Git trust on exFAT or FAT). Nothing is written to `~/.gitconfig`, so a reinstall or a new machine needs no setup. Running git by hand in that repo still needs `safe.directory` or `GIT_CONFIG_*` set.
- macOS mounts an NTFS drive read-only. A board whose repo or data folder is on one stops at start with "unable to open database file" (`openDb`: board.db in WAL mode cannot create its `-wal`/`-shm`). exFAT works on both systems; WAL, `settings.lock` and the voice download all work on it.
- Probing a second shell beside a live board on macOS: set `KANBAN95_HOME` and `KANBAN95_SHELL_LOG` to scratch paths, or the probe's failures land in `~/Library/Logs/Kanban95/shell.log` and read as the operator's. `npm run dev` and the shell binary itself refuse while `KANBAN95_AGENT` is set (every agent's pty has it), so an agent cannot open a board window; probing the shell is the operator's. The installed shell can be probed by running `/Applications/Kanban95.app/Contents/MacOS/kanban95-shell <repo>` directly, with `KANBAN95_UPDATE_URL` for a local `latest.json`.

**Tests**
- Imports between `src/` files use `.js` extensions; tests import `../src/x.ts`.
- Node's `fetch` strips a caller-set `Host` header; a test that needs a foreign `Host` uses `node:http.request`.
- An unclosed MCP SDK client keeps vitest alive; close every client in `afterAll`.
- Every test file runs with a throwaway home (`daemon/test/home.ts`), and `daemon/test/real-home-guard.ts` fails the run if the real home was touched by this run: it points `TEMP`/`TMP` at a fresh `k95-run-*` dir before the workers start and fails only on trust entries under it, so another worktree's run at the same time cannot fail yours (`docs/SECURITY.md` → Operator files the board writes). Keep it that way.
- `start()` commits a repo that has no commit, or `git init`s a plain folder and commits it (Daemon lifetime → First start on a plain folder). The test home has no `~/.gitconfig`, so there that commit fails and every ticket launch fails with `gitError`. A test that launches commits (with a repo-local identity) before `start()`; one that wants the daemon to commit writes `~/.gitconfig` in the test home (`git-init.test.ts`).
- Headless Edge resizes its window to `--window-size` minus chrome; `cdp.ts` sets the viewport with `Emulation.setDeviceMetricsOverride` to get an exact size.
- Windows resolves LocalApplicationData from `%USERPROFILE%`, and to an empty path when `%USERPROFILE%\AppData\Local` is missing. PowerShell then writes its `Microsoft\Windows\PowerShell\ModuleAnalysisCache` into its cwd, which under vitest is `daemon/`, and it got committed once. `test/home.ts` creates that folder in the test home (`test/test-home-local-appdata.test.ts`).
- Headless Edge 155 never opens its DevTools port when `%USERPROFILE%\AppData\Local` is missing: every UI test then times out in `beforeAll`. `launch()` in `cdp.ts` starts the browser with a throwaway home of its own (USERPROFILE, since vitest's `globalSetup` runs with the operator's real one) and creates that folder in it. If the UI tests all time out at "the DevTools port" after a browser update, start the browser by hand with the test's environment first. A browser that exits before writing `DevToolsActivePort` fails `launch()` at once with its exit code instead of after 60 s, and any failed start kills the process and deletes its `k95-browser-*` dir (`test/cdp.test.ts`).
- `/events` carries several frame shapes; anything listening must ignore frames it does not know.
- The silence watch (`watchSilence`, `docs/LIFECYCLE.md` → Silent agents) arms its first timer when `start()` runs. A test that shortens `SILENCE` does it in a `beforeAll` of its own describe, which runs before the outer `beforeEach` starts the daemon, and restores it in `afterAll`; anywhere else a shortened limit flags every fake agent that stays up. A session's silence counts from its spawn, not from the fake's first line, and the fake's `node` took 1.5 s to start with the suite run from an agent's terminal on a loaded machine: a 400 ms limit flagged the fake before it printed (terminal `(nothing)`) or wrote its transcript. `lifecycle-silence.test.ts` holds `idle_minutes` high until the fake has printed, then drops it to 1 (`up`).
- `daemon/vitest.config.ts` sorts test files into projects by their imports (`sortTests` in `test/projects.ts`, which `test:changed` shares): `unit` (no retry: a unit failure is real), `pty` (imports `../src/launcher.ts` or `./board.ts`; 30 s per test and hook; `retry: 1`, since on a loaded machine a process Windows fails to start or a 30 s wait running out fails a test that passes on its second run), `browser` (imports `./cdp.ts`, which every `ui-*.test.ts` does; `retry: 1`, and each retried test prints a `RETRIED x1:` line) and `restart` (alone, last). `unit`, `pty` and `browser` run as one group on one shared worker count; `restart` runs after them. A new file needs no config entry. Each browser file starts its own daemon but no browser: the browser project's `globalSetup` (`test/browser-setup.ts`) starts one headless Edge or Chrome per run and puts its DevTools port in `K95_CDP_PORT`, and `browser()` in `cdp.ts` opens a tab in its own browser context (own cookies and storage) and `close()` closes only that tab. The shared `beforeAll` in `test/ui.ts` (daemon start, tab, first load) takes about 1 s idle but measured up to 25 s with four browser files in parallel beside other tickets' tests, so it has 90 s. Outside vitest (a screenshot script), `browser()` starts a browser of its own. A daemon's `close()` drops the browser's keep-alive sockets (`closeAllConnections`); without that, one held socket kept it waiting 30 to 60 s. The worker count comes from the machine (`workers()` in `daemon/test/projects.ts`, read once per run): one per 2 GB of total memory, at most 6, at most one less than `os.availableParallelism()`, at least one (an 8 GB machine runs 4). vitest refuses two projects with different worker counts in one group. The lifecycle scenarios are split over `lifecycle-*.test.ts` (setup in `test/board.ts`) so that no one file is the whole critical path. Keep each pty file under about 45 s; a file's tests run one after another in one worker. `tsc` is incremental (`dist/.tsbuildinfo`).
- The full `npm test` has a budget: at most 5 minutes on the operator's 8 GB Mac, 2-3 preferred. Measured 2026-10-13 on that Mac, one project at a time: `unit` and `restart` 41 s, `pty` about 100 s, `browser` 66 s. Each real pty or browser test costs 1-10 s (a daemon, a git repo, a node fake agent per launch, a merge), a unit test milliseconds. So only critical paths get a real pty or browser, and a new test of anything else goes in a unit file. Real ptys run in: `launcher.test.ts` (launch, env allowlist, grant revoke, pty websocket), `kill-tree.test.ts` and `setup-cancel.test.ts` (no orphaned processes), `conhost.test.ts` and `darwin-no-powershell.test.ts` (platform), the `lifecycle-*.test.ts` files (launch -> execute -> test -> merge, conflicts and the merge queue, push, restart and resume, the stale daemon, the silence watch, worktree_setup), `runner.test.ts`, `release.test.ts`, `restart-hold.test.ts`, `git-init.test.ts` (first start), `refused-mutation.test.ts`, `reset.test.ts`, `memory-hold.test.ts` and `operator.test.ts`. The browser smoke set is six files: `ui-board` (drop, launch refusal, Run/Stop, Push), `ui-terminal` (a terminal's lifetime, End and Resume), `ui-inbox` (an answered question, a failed merge), `ui-setup` (first start), `ui-release` (release pending, Release board, the stale-daemon restart badge) and `ui-update` (the update dialog). UI details (taskbar, window placement, zoom, notepad, voice) are checked by hand in the dogfood cycle, not by DOM tests.
- A file-level `beforeEach` runs before every test in the file, also in a `describe` written above it. A pure test (a table, a parser) in a file whose hooks make a repo and start a daemon pays that start every time: the 34 transition-table rows took 15 s that way and take 25 ms on their own. Put pure tests in a file with no such hooks (`lifecycle.test.ts`, `argv.test.ts`).
- Two test commands (`docs/AGENTS.md` → Verification): `npm test` (`tsc` and the full suite) is the operator's, run by hand only, never by the board; `npm run test:changed -- <base>` (`daemon/test/changed.ts`, no `tsc`) runs only the tests the worktree's changes against `<base>` can affect, and is what both the worker and the tester run. vitest's module graph cannot see `ui/`, `templates/`, `skills/` or docs, so `changed.ts` maps those paths to tests; a new test that reads such a file needs a row there. Only unit tests follow the module graph; pty, browser and restart files run only when they import a changed file themselves or through a changed test helper (every browser file for a `ui/` change; `--pty`, `--browser` for all of one kind): a `daemon/src` file no ui test imports runs no browser test. `test:changed` needs `daemon/dist` current for `server.test.ts`: run `npm run build` too.
- A browser or pty test that fails twice, or a unit test that fails once, is a real failure (no test runs more than twice); a `RETRIED x1:` line is load, but the same test retried run after run is not; rerun the file alone only to tell your change from load.
- A test whose agents only have to count as running needs no pty: `runner.test.ts` mocks `../src/pty.ts` so a `--model hang` agent gets an in-process stand-in (no `cmd.exe`, `claude.cmd` or node), and every other model still spawns a real one. A ConPTY spawn and its kill cost about a second each under load; the pty path itself stays covered by `launcher.test.ts` and the `lifecycle-*.test.ts` files.
- A UI test that needs a window place, layout or folded column set in advance sets it in the open page's `state.js` cache (`import('/state.js')`, then `set`), so the live page sees it at once, and waits until `ui.json` has it, so a reload right after keeps it. State the page saved by itself (a typed filter, a moved window) also needs that wait before a reload: the page's pagehide flush is a keepalive PUT that the next page's `GET /api/ui` can beat under load, and the reloaded page then shows the old state. Writing `ui.json` or `PUT /api/ui` from the test while a page is open loses to that page's next write of its own copy. A UI test may start a second daemon in the same browser: each daemon's cookie is `k95-<port>` (cookies ignore the port, so one shared name would let the second login replace the first), and the first board is still logged in afterwards.
- With nothing saved, Done starts folded (a folded column renders no cards, so `column(id)` is null for a Done ticket): a UI test that needs a Done card presets `k95.collapsed` in `state.js` and reloads. Terminals tile into the `SLOTS` region, so test `place()` with a plain `wm.open` window.
- `cdp.ts` starts the browser with `--mute-audio`. Headless still plays sound, and the UI tests' merges and questions send the board's ding and chord with the test home's default settings (sounds on): unmuted, every test run chimed on the operator's speakers with nothing on the board to explain it.
- Killing a pty before the fake agent printed its first line crashes the vitest worker natively on Windows (exit `0xC0000374`, heap corruption in node-pty): wait for the fake's first output, then `killTree(s.pty)` and await `done` (`end()` in `launcher.test.ts` and `operator.test.ts`). `killSession`'s sweep ends a fake `node` that `cmd.exe` was still starting at the kill, which used to outlive the run and lock its worktree under the test home (EPERM at the home's removal). The native crash and a kill that never exits are not fixed by it. `srv.close()` kills every pty, so the pty files still wait in `afterEach` for every live session to have printed (`test/board.ts`, `runner.test.ts`, `launcher.test.ts`), for the crash, and a test that restarts or ends a session waits for its output first.
- A submitted ticket's tester waits in a queue while free memory is under 1 GiB (`queueTest` in `daemon/src/lifecycle.ts`), so on a busy machine a test that expects a tester after a submit sees none. A test file that expects one imports `./memory.ts`, which stubs `memory.free` above the floor before each test and restores it after; `test/board.ts` and `test/ui.ts` already do. A test of the queue sets its own low value after that (`tester-queue.test.ts`).
- On macOS `os.freemem()` is near zero all the time (the kernel's free list only; inactive and purgeable pages are not counted), so a memory check built on it holds forever. Use `freeMemory()` from `daemon/src/memlog.ts`, which reads `vm_stat` on darwin, or `memory.free` in `lifecycle.ts`.
- Ticket worktrees live outside the repo, under `<board home>/worktrees/<repo key>/` (`worktreesRoot` in `daemon/src/git.ts`); in tests that is under the file's throwaway `KANBAN95_HOME`, so a test builds a worktree's path with `worktreePath(repo, id)`, never by joining it onto the repo. Removing a test repo does not remove its worktrees; the throwaway home goes at the end of the file.
- A ticket worktree gets its own dependencies: run `npm install` (or `npm ci`) in the worktree with Node 24 on PATH. Never junction or symlink the main checkout's `node_modules`, or anything else of the main checkout's, into a worktree. `git worktree remove --force` followed such a junction (and `node_modules/@kanban95/daemon` inside it) and emptied the main checkout's `daemon/`. The janitor now unlinks every link in a worktree before removing it and refuses when a link into the main checkout will not let go (`docs/LIFECYCLE.md` → Janitor), but a link is still a way to break main from a worktree: any tool that writes or deletes through it reaches main's files.
- The UI is CSS-zoomed on `body` (operator's `zoom` setting). Pointer coordinates and `box(el)` from `wm.js` are screen px, offsets and inline styles CSS px before zoom: divide by `scale()` from `wm.js` before writing a screen value to a style. A UI test that changes the zoom resets it with Ctrl+0, since it persists in the test home's `settings.json`.
- WebKit coordinates under CSS zoom: the Mac app's system WKWebView (Safari 18.5, macOS 15.5, checked 2026-10-13) returns `getBoundingClientRect` in CSS px before zoom, while `clientX`/`clientY` and `elementFromPoint` stay screen px. Chromium and Playwright's newer WebKit (27.2, what `npm run shot` uses) return screen px for both, so `npm run shot` does not show this; `npm run shot:mac` does. `wm.js` detects it once at load with a hidden `zoom: 2` probe (no user agent check) and `box(el)` multiplies by the zoom only there. Never call `getBoundingClientRect` directly in the UI; use `box(el)`.
- WebKit paints under CSS zoom: the Mac app's WKWebView smears 98.css's `border-image` bevels (fieldset, `.sunken-panel`) at a zoom that is not a whole number. On macOS both WKWebView and Chrome draw extra `::-webkit-scrollbar-button`s (`:start:increment`, `:end:decrement`) unless they are `display: none`. `ui/app.css` draws both bevels with 1px `linear-gradient` background strips on a 2px transparent border and hides the extra buttons. A new bevel uses borders, box-shadow or such strips, never `border-image`; a fieldset or `.sunken-panel` that sets the `background` shorthand wipes its bevel. Playwright cannot show this; check in a WKWebView (global brain row on WebKit zoom).
- Terminals tile (`retile` in `wm.js`, 50 ms debounced) and save no place: a UI test asserts terminal geometry inside `until()`, and an emulated viewport change is seen by the page a moment later, so wait for the windows to have scaled, not just for the desktop size. A terminal smaller than `.k95-win`'s 220×120 minimum spills out of its slot: test grids in a region wide enough for them.
- Moving an element in the DOM (`after`, `before`) drops its pointer capture. A reorder drag listens on `window`, as `dragCard` and `dragTask` do.
- Several tickets run at once and every branch merges into the same files. Put a new test in its own `daemon/test/<feature>.test.ts`; a new UI test goes in a `ui-<area>.test.ts` and imports `./ui.ts` for the daemon and browser. In the other hot files (`daemon/src/api.ts` route table, `ui/app.js`, `docs/*.md`) add new routes and UI blocks next to related ones rather than at the end, and new doc content as its own section.
- `api.ts` and `mcp.ts` import each other. A value from `api.ts` read while `mcp.ts` loads (inside the `TOOLS` table, not inside a `run`) is in its temporal dead zone when the built daemon starts from `dist/server.js`: `server.test.ts` times out with "Cannot access X before initialization" while the vitest files that import `api.ts` first pass. Put such constants in a leaf module (`db.ts` holds the brain ones).

## How the board was built

Planned on 2026-10-07 as nine phases, each a handoff prompt run by a fresh agent that wrote a log entry for the next. Phases 0 to 2 (scaffold, daemon core and grants, MCP) were built by hand with Claude Code; from phase 3 (templates) on the board built itself, ticket by ticket. Phase 8 (2026-10-08) shipped the agent skills, finished `docs/`, and ran two dogfood cycles: a throwaway sample repo brainstormed into five dependent tickets that all merged with no `needs_human` flag (the walkthrough and its manual touches are in `docs/OPERATOR.md` → Dogfood walkthrough), then this repo, whose improvements are now brainstormed and launched on its own board.

What changed when the build plan was retired:

- The build plan (the spec) and the phase handoffs with their log are deleted. Everything still true moved into the living docs: the design principles and conventions into `CLAUDE.md`; decisions into the doc of the part they shape (`SECURITY.md`, `CLIS.md`, `LIFECYCLE.md`, `AGENTS.md`); the gotchas from the phase log into Working on the board above, `SECURITY.md` and `CLIS.md`. Per-phase deviations that the docs already describe as the current design were not repeated.
- New knowledge goes where it applies: a behaviour change into its living doc in the same ticket, a gotcha a future ticket would trip on into the brain (`brain_add`) and, when it is about the code itself, into Working on the board. There is no phase log any more; the board's notes, runs and brain are the record.
- Housekeeping now has only the living docs, plans and proposals to judge: with no build plan or handoff left, a run on a clean repo should report nothing to change.
